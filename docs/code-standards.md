# 代码规范

本文件保存从 [LESSONS.md](../LESSONS.md) 中验证成熟的项目规范。开发与审查只对照本次改动适用的条目；规范中的例外和边界也是规则的一部分。

## 当前规范

当前没有满足下述条件的已升级规范。现有经验保留在 `LESSONS.md`，历史复盘日期不作为已核实的独立事件计数。

## 升级规则

一条经验同时满足以下条件时，代理在本次授权的经验维护中完成升级，无需增加审批步骤：

1. 至少有三个发生在不同日期的独立真实事件。每个事件有稳定 ID、实际发生日期、来源仓库、失败场景与可复核的提交或 Issue 证据。日期按 `Asia/Shanghai` 归一，不能用审核日期或补写日期代替未知的发生日期。
2. 重复审查、同一次故障的连续修补、跨页面推广、同一补丁的 cherry-pick 均归为同一事件；同日多个独立事件保留各自证据，但升级门槛只计一个日期。
3. 已核实这些事件具有相同的可推广根因，明确本项目内的适用范围、例外和替代做法。跨仓库事件仅在已核实且技术条件一致时作为补充证据，不能仅凭相似提交标题计数。
4. 已检查与用户当前指令、全局约定及现有项目规则的兼容性。存在冲突、未核实证据或边界不清时保留为待完善经验，不自动升级。
5. 有具体且适度的检查方法：已有测试、必要的新回归测试、静态检查或可复现的人工验证。不能只写“加强测试”或要求所有改动运行全套检查。

计数达标后仍须完成第 3–5 项判断。没有达标不妨碍及时修复已确认的缺陷；这里约束的是长期规范的形成。

## 规范记录与归档

每条规范包含：稳定规则 ID、规则、适用条件与例外、原因、检查方法、来源事件 ID/日期/仓库/提交或 Issue，以及升级日期。

升级时在同一提交中完成两处变更：在本文件建立规范；将 `LESSONS.md` 对应条目移到《已归档》，保留完整历史证据并链接规范。建立首条规范时，同时在 `CLAUDE.md` 恢复 `@docs/code-standards.md` 导入，并删去其中“尚无已升级规范”的说明。不要保留两份可独立编辑的规则正文。若现有规则已经覆盖该经验，应合并证据与适用边界，避免新增重复规则。

规则失效时记录失效原因、日期和替代规则，不抹去历史依据。只编辑本次负责的内容；遇到并发修改先重新读取并合并，不通过覆盖文件解决冲突。
