# 统一交易与资产平台方案

版本：草案 v0.1，2026-11-10。源码基线：`a12e583`。状态：**待确认**，第 12 节的三项前提确认前不据此实施。

本文回答"如果重新设计，这个项目应该是什么形状，以及怎么从现状走过去"。它与[技术与架构演进](evolution-plan.md)的关系见第 11 节。结论来自 2026-11-10 的一轮只读调研，证据见附录；调研没有修改代码，也没有做任何实盘或性能测量。

## 1 定位与前提

把监控、交易、策略、账本和研究建在同一套账户、合约和执行模型上：一个前端、一个仓库、四个后台进程、统一发布和一键部署。

方案按三个前提设计：

- **单机、自用或小团队。** 表结构保留用户归属字段，但不做多主机。
- **在现有仓库内分阶段完成，不开新仓库。** 前三个阶段不依赖重写执行；开新仓库只会多出重建发布链的成本。
- **运行时最终只有 TypeScript。** Python 只留给离线回测和研究工具。

重建的主要收益不在执行引擎（Hub 的引擎已实现大部分设想，见附录 A.2），而在四处合并：公共行情客户端、存储、凭据、前端。业务逻辑本身压不掉多少，能省的是重复实现和模块之间的胶水。

## 2 产品组织

旧模块的功能归入按业务划分的工作区：

| 工作区 | 承接的功能 |
| --- | --- |
| 总览与资产 | 全账户资产、持仓、手工资产、历史导入、出金登记、汇率换算、收益 |
| 市场与机会 | 行情、价差、资金费、机会筛选、上新与额度监控、告警 |
| 交易中心 | 原生跨所交易、Gate CrossEx、预览确认、开平仓、订单与任务追踪 |
| 策略与风险 | 自动开平、ANT 减仓与仓位保护、ASTER 开仓、保证金平衡、ADL |
| 期权 | 期权链、Greeks、组合分析、策略计划、RFQ |
| 链上 | Aero 池研究、Safe 仓位、LP 开平、自动调仓 |
| 研究室 | 成本模拟、行情回放、回测、报告归档 |
| 系统 | 账户连接、通知、诊断、服务状态、备份恢复、更新 |

每项功能在功能矩阵里标明**只读、模拟、实盘（已验证或未验证）、已移除**。这张矩阵就是验收清单，是阶段 0 的首个交付物。

## 3 技术栈

| 部分 | 选择 | 说明 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite | 一个应用，统一路由、组件、表格和图表，取代现在的 iframe 加四套构建 |
| 后端 | Node.js、TypeScript | 接口契约、适配器、策略和执行核心共用类型 |
| 数据库 | SQLite WAL | 改用 PostgreSQL 的条件是出现多主机或持续写争用，与[演进第 6 节](evolution-plan.md#6-容量与后续架构的进入条件)一致 |
| Python | 仅离线工具 | 期权回测和研究；不进运行时 |
| 部署 | systemd，发布目录加原子切换 | 保留两阶段更新和摘要锁定目标 |

不选 PostgreSQL 的理由：安装和大版本升级需要 root；备份恢复要从拷文件改成导出导入，现有恢复工具全部作废；目前没有写争用的证据。

## 4 运行时

```
web ──> api（登录、查询、配置、指令受理；可独立更新）
          │
          ├──> executor  执行引擎 + 策略规则 + 自己订阅的盘口 + 所交易账户的同步
          │       └──> 交易所 / 链上
          ├──> feeds     展示用行情、机会扫描、只读账户同步、告警触发
          └──> jobs      研究、回放、飞书汇总、Aero 池研究、回填
```

- **策略与执行同进程。** 规则状态与任务、合约锁在同一事务提交，引擎每批发送前要重算策略的触发条件（附录 A.2）。
- **执行依据的盘口由 executor 自己订阅。** 现有的新鲜度窗口（1500 毫秒）按本进程收到的时刻计，不能经数据库或另一个进程转交。
- **重负载全部放在 jobs。** 已证实的卡顿来自研究任务同步落盘拖停行情流。
- **executor 只做执行相关的事。** 它的同步落盘是否会阻塞事件循环，建成后先实测再定。

## 5 五个基础

### 5.1 账户与合约身份

- 账户按交易所、环境、真实账户和子账户识别，换 API Key 不产生新账户。
- 合约保留原始代码、类型、结算币和乘数；链上资产保留链和合约地址。
- 展示名只用于关联，不能授权下单。

### 5.2 数据有效性

- 每份数据带来源时间、接收时间和有效性；过期、缺失、真实零值分别处理。
- 这些做成类型，并在交易所返回和进程间消息的边界做运行时校验。
- 同一场所、合约、通道的公共行情只订阅一次，以 Monitor 扫描器现有的 12 个适配器为起点。

### 5.3 执行

基本链路：

```
意图 → 校验与授权 → 落盘与预占 → 发送前一刻复核 → 明确回执或结果未知 → 核对 → 完成或待处理
```

- 意图带可由引擎重算的守卫条件。
- 引擎支持可恢复的多步流程；普通订单、多腿、RFQ、划转、链上交易各有专用状态机。
- 每个适配器自己声明"用什么做幂等身份"和"结果未知时如何结算"，不假定都有客户端订单号。
- 保留防旧进程残留写入的栅栏、持久操作状态和凭据身份复核；去掉双语言实现和模块间账户归属协议。
- 现有 Hub 执行引擎的状态机直接移植，不重新设计。
- 开仓、减险、资金管理分别定义准入条件；暂停策略后，已发送订单的核对继续进行。

### 5.4 账本与口径

- 成交、手续费、资金费、划转、估值分别保存，并保留交易所原始上报值。
- 流水从接入日起累积；早于各所回看上限的历史以交易所报告为准。
- 总资产收益保留余额差分算法。
- 每次同步与交易所余额和仓位对账，差额记为"未解释"。
- 模拟收益、资产变动、已实现收益分开展示；缺失的成本和入金保留缺失。

### 5.5 可追踪与可恢复

- 业务状态和待发送事件在同一事务保存，通知、账本更新、页面状态按事件身份去重消费。
- 实时盘口走内存分发，只按需保存研究样本。

## 6 存储与凭据

- **两个库。**
  - 权威库：账户、任务、订单、规则、流水、事件。执行与流水相关的表只由 executor 写，配置表由 api 写，表的写入归属用测试固定。
  - 可重建库：行情、采样、缓存。由 feeds 和 jobs 写，不进备份。
- **一条迁移链。** 有序 SQL 加哈希校验，沿用 Asset 现有做法；遵守先扩后收，保证可回滚一个版本。
- **一套凭据密钥。** 合并现有三套密钥和三种密文格式，消除明文 `.env`；备份清单同步升版本。合并前先定同一账户在 Hub、Asset、CrossEx 的三份凭据以哪份为准。

- 部署骨架从阶段 1 开始随每个阶段交付。
- 阶段 5 是工作量和风险的大头：约 2.3 万行非测试 Python 的状态机和约 4.5 万行测试。
- 经验条目的处理：盈亏口径、缓存时效、迁移、幂等这几类转成类型和契约测试；交易所行为约 15 条只能靠录制夹具和实盘保留；部署类约 21 条绑定现有安装器，按新部署方式重新核对。
- 整体工作量没有估算，阶段 0 的功能矩阵完成后给出。

## 8 账户接管规则

- 新系统先只读运行，对照仓位、流水、行情和交易预览。
- 接管一个账户时：停止旧写者 → 核对在途操作 → 导入最终状态 → 放开新执行器。
- 涉及多个账户的策略整体交接。
- 无法可靠接管的未知任务留给旧执行器核对，该账户暂不切换。
- 新系统开始交易后，回退必须交接新增订单和流水，不能用旧库覆盖已发生的成交。

## 9 部署与验收

- 正式包由 CI 构建并固定版本和摘要；安装器一条命令完成依赖、配置和服务注册，可重复执行，无变化快速结束，只重启受影响的进程。
- 两阶段更新（先准备、后切换）保留；api 可单独更新而不中断 executor。
- 验收重点：
  - 未知订单恢复、旧写者退出。
  - 行情过期、限流、部分成交。
  - 链上交易确认。
  - 备份恢复。
- 验证环境是 Linux 服务器和 Linux CI。
