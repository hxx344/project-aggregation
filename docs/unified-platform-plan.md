## 1 定位与建设边界

把监控、交易、策略、账本和研究建在同一套账户、合约和执行模型上：一个原生前端、一个仓库、少量隔离的后台进程、统一正式发布与一键增量部署。

已确认近期场景为自用、单台 Linux 服务器；首批业务闭环优先原生交易中心的 ANT／原油，最终仍覆盖当前有效功能。服务器资源、首批交易所和代表性负载在阶段 0 登记。“单机”本身不能决定数据库是否适合；选择条件见第 3、6 节。多租户与多主机不是本轮功能对等的验收项。

**建设方式按执行依赖和切换风险划分，不能只看组件是否直接发送订单。** 行情、账户与合约身份、预览和确认表单都可能参与交易决策；这类读路径或前端改动仍需验证对应的执行契约。

| 部分 | 方式 | 理由 |
| --- | --- | --- |
| 展示、扫描、研究所用公共行情与只读页面 | 在现有系统内逐个收敛到共用层 | 可按业务切片交付；先核对调用方，确认替换没有改变仍在运行的执行依据 |
| 交易相关行情与身份读取、预览确认和任务操作页面 | 先保留旧执行路径的语义与数据来源；按对应守卫、时效、失效和恢复契约验收后切换 | 接口只读或改动位于前端，也可能改变下单对象、数量、触发条件和证据年龄；不能归为纯展示改动 |
| 执行器、策略守卫、业务权威库、凭据管理 | 同仓独立建设，独立代码入口、数据目录、启动配置和迁移版本；旧执行路径继续运行，按账户分批接管 | 新旧执行权需要明确隔离；跨语言状态机的移植范围和成本在阶段 2b 核验 |

独立建设的部分不直接写旧库，也不通过逐步修改旧模块来隐式取得实盘账户控制权。开发期间通过独立工作区隔离修改。复用现有安装发布工具、交易所规则、计算案例和测试向量，复用前核对其适用范围。

两种方式各自的代价：

- 原地演进的部分会有新旧表达并存的过渡期，每个调用方需要适配；必须为每一项设定“旧实现删除”的完成条件，防止停在半路。
- 独立建设的部分在账户接管前没有实盘收益，并且要与旧执行路径并行维护，规则见第 1.1 节。

### 1.1 新旧并行期间的规则

- **新增功能的落点。** 展示、扫描、研究和独立告警功能优先做在共用层。供执行器使用的读数据按执行契约验收后才接入，不因接口只读而降低验证要求。执行与策略类新功能在对应账户接管前仍做在旧执行路径，并同步登记到功能矩阵和新执行器的待办；不为等待新执行器而暂停业务需求。
- **交易所行为修复。** 旧执行路径的每个交易所行为修复，同时产出一份录制夹具或契约测试，新连接器以同一份夹具验收；修复不靠人工在两边各改一遍来保持一致。
- **冻结点。** 某个策略或模块进入阶段 5 的移植后，其旧实现只接受缺陷修复，不再加功能；该模块的账户全部接管并过了回退观察期后，旧实现删除。
- **功能矩阵的基线。** 矩阵记录所对照的旧系统提交；旧系统合入影响矩阵的改动时更新对应行，接管验收以更新后的矩阵为准。
- **请求额度与连接数。** 新旧系统在同一台机器上共用交易所实际按 IP、账户和 API Key 等维度计的额度。展示、扫描和研究以共用行情层复用订阅；新旧执行器的专用行情是第 4.1 节明确保留的例外。新执行器在只读或模拟期间只为正在验证的账户与合约建立连接，按旧系统的额度余量设置上限，额度不足时让新系统退避。

“从零设计”指重新确定领域、模型和契约，不要求丢弃已验证算法。是否另建仓库属于交付管理选择，不由数据库或语言决定；当前先复用本仓发布基础，避免把仓库迁移变成验证新架构的前置条件。阶段 0 至 2b 实质上是一次原型验证：数据库、语言边界和进程划分都在这之后才冻结（第 12 节）。

TypeScript 是新核心的默认语言。未接管的 Python 模块按原有归属运行；过渡期及接管后的执行边界见第 5.3、8 节。统一账户和执行模型不以全部 Python 退役为前提。

## 2 产品组织与功能范围

| 工作区 | 承接的有效功能 | 必须保留的边界 |
| --- | --- | --- |
| 总览与资产 | 账户资产、持仓、手工资产、历史导入、出金登记、汇率换算、资产变化及已有盈亏核算 | 出金登记不代表发起提现；不同标的的账本覆盖分别记录 |
| 市场与机会 | 行情、盘口、价差、资金费、机会筛选、上新与额度监控、告警 | 机会和退出成本估算不代表已下单或可保证成交 |
| 交易中心 | 原生跨所交易、Gate CrossEx、预览确认、开平仓、订单与任务追踪 | 保留各交易所、账户模式和合约的能力范围 |
| 策略与风险 | 自动开平、ANT 减仓与仓位保护、ASTER 单账户普通开仓、配对保证金平衡和 ADL | ASTER 已移除的配对普通开仓、循环与仓位迁移不恢复为新需求 |
| 期权 | 期权链、Greeks、组合分析、策略计划、开平仓任务、RFQ | 订单与 RFQ 分别核对幂等、报价有效期和未知结果 |
| 链上 | Aero 池研究、Safe 仓位、LP 开平、质押、领取、兑换及自动调仓 | 保留链、Safe、Roles 权限和多步交易恢复语义 |
| 研究室 | Entropy/Lighter、Binance/Lighter 成本模拟、回放、回测、报告归档 | 研究会话与实盘账本分离；既有纸面工具不隐式增加实盘能力 |
| 系统 | 账户连接、通知、诊断、服务状态、备份恢复、更新 | 页面关闭不停止后台任务；状态分别表示存活、就绪和业务可用 |

阶段 0 建立功能矩阵，逐项记录：实际入口、数据来源、只读/模拟/实盘/已移除、代码与测试证据、是否实盘验证、迁移去向和验收案例。保持功能对等不要求复现已知错误；修正旧口径时同时保留原历史含义和差异说明。

Lighter 公开市场研究与原生交易、资产中的 Lighter RH 分别建模，不因显示名相似合并场所或账户。新平台的统一全品种核算属于需明确覆盖范围的建设目标，不能描述为现有各模块已经完整提供。

## 3 技术选择及冻结条件

| 部分 | 首期选择 | 冻结条件 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite，一个应用 | 先完成首个业务切片，再逐个承接工作区 |
| 新业务核心 | Node.js、TypeScript | 契约有运行时校验；执行行为与恢复样例通过 |
| 事务存储 | SQLite WAL，作为单机原型的首选候选 | 第 6 节混合负载与恢复验证通过后，在批量历史迁移前冻结 |
| Python | 未接管模块继续运行；计算、研究或策略可按需保留 worker | 每个模块分别验证迁移收益、时序与行为对等 |
| 部署 | systemd，独立版本目录、准备后激活、统一正式包 | 增量更新、失败回退与真实服务入口验收通过 |

选择 SQLite 的有效理由是单机部署简单、现有工具与经验可复用。**按表划分写入者不能消除同库的写锁竞争**，旧系统未观察到争用也不能代替新布局的验证。[SQLite WAL 官方说明](https://www.sqlite.org/wal.html)明确同一数据库同一时刻只有一个写者。

PostgreSQL 是以下情况的替代选择：确需跨主机权威写入，或在短事务、有界回填、合理索引和存储调用隔离后，SQLite 仍不能满足已确定的执行时效与维护预算。届时先调整存储设计和恢复适配，再进入大规模导入；首期交付只实现最终选定的一种后端。

PostgreSQL 增加数据库服务及升级维护成本，但并非必须以 root 安装，备份也包括文件级备份、基础备份与 WAL 归档。现有 SQLite 快照和结构检查需要适配，版本清单、密钥保护、隔离恢复和唯一写者交接原则仍可复用，不能称为恢复工具全部作废。参见[安装说明](https://www.postgresql.org/docs/current/tutorial-install.html)与[备份恢复说明](https://www.postgresql.org/docs/current/backup.html)。

Greeks 当前直接依赖及计算方式未显示必须保留 Python 科学计算栈，见附录 A；这支持评估迁移可行性，不代表迁移所有 ASTER/RFQ 状态机已经划算。全 TypeScript 作为后续收敛目标，不阻塞业务功能对等交付。但接管规则本身已经决定了大部分去留，见第 5.3 节末尾。

## 4 运行时与行情边界

以下是四类运行职责；研究计算可使用受限子进程或 worker，不将进程数量固定为性能目标。

~~~
统一前端 → api：登录、查询、配置与幂等指令受理
              ├→ executor：执行准入、轻量策略守卫、账户同步、核对与恢复
              │             └→ 交易所 / 链上
              ├→ feeds：公共行情、机会扫描、只读账户采集、告警信号
              └→ jobs：研究、回放、历史回填、通知投递
~~~

API 独立更新不应中断采集和执行。jobs 内的计算与批量 IO 使用有界队列和隔离 worker，通知调度不能因一次回放长期饥饿。进程生命周期、停止预算和私有 IPC 契约随原型验证，不沿用未经核对的旧超时常量。

### 4.1 公共订阅与执行专用订阅

- feeds 统一复用展示、扫描和研究所需的同场所、合约、通道订阅。
- **首版允许 executor 为正在交易的合约保留专用行情连接。** 这是明确的重复订阅例外，不再承诺全系统每个通道只有一条连接。
- 未接管的旧执行器同样保留其专用行情客户端。阶段 1 不以删除这些客户端为退出条件；后续替换须证明来源身份、原接收年龄、盘口完整性、断线恢复和最终发送守卫保持有效，再按执行相关变更切换。
- 两者复用连接器实现、目录校验和限流契约；按交易所真实的 IP、账户、API Key 等额度域共同约束请求，不能每个进程各拿一整份额度。
- 执行订阅只覆盖必要合约，并保留来源时间、本地接收时刻、序列、连接代次及失效原因。展示快照可以保留旧值，执行证据须在发送前重新核验。
- 向页面或研究转发执行行情，不得阻塞执行接收和发送；积压按通道语义有界处理。需要完整序列的盘口增量发生丢失时，必须失效并重建快照。

现有 Hub 的 1500 毫秒双腿读取窗口是当前实现约束，不证明跨进程行情不可行。若后续合并执行采集，必须保留原接收年龄和序列，计入 IPC 排队时间，核验时钟语义、生产者重启代次和消费者落后；转发接收时间不能覆盖原始接收时间来“刷新”旧报价。未通过同等时效验证前保留执行专用订阅。

### 4.2 策略与执行

轻量触发计算和最终发送守卫优先放在 executor。复杂研究与计算产生候选意图，不能直接取得交易凭据或绕过执行准入。

策略状态、任务、资源预占和业务事件需要原子提交，是事务边界要求，不等于所有计算必须同线程完成。网络读取和复杂计算在事务外执行；提交和最终发送的版本校验见第 6.2 节。

## 5 共同业务契约

### 5.1 账户、合约与金额

账户按场所、环境、真实账户及子账户身份识别，API Key 轮换不生成另一个主体。跨场所账户或 CrossEx 底层归属只有取得身份依据后才关联，不能按展示名推断。

合约保留原始 ID、类型、结算币、乘数与数量规则；链上资产保留链 ID 和合约地址。统一展示标的与可执行合约分别保存。金额及交易数量采用精确十进制或原始整数，币种和单位显式携带；换算保留汇率来源、时点和缺失状态。

### 5.2 数据有效性

交易所响应及进程间消息在边界做运行时校验，类型定义不能替代输入校验。每份观测保留来源与接收时间、完整性、序列或版本、连接代次及失效原因。

过期、缺失、不完整和真实零值分别表达。历史修补与近期增量使用独立进度；只有完整读取与持久合并成功才推进水位，失败保留原记录和绝对重试期限。跨进程消息不得把局部成功升级成完整账户或完整历史。

### 5.3 执行、恢复与 Python 过渡

~~~
意图 → 校验与授权 → 持久化及预占 → 最终发送复核
     → 明确回执或结果未知 → 原操作核对 → 终态或待处理
~~~

复用 Hub 已验证的发送前守卫、幂等、未知结果核对和旧写者隔离规则及测试，逐项证明新模型仍满足这些规则。**不承诺原样移植 Hub 状态机即可覆盖所有业务。** 普通订单、多腿、RFQ、划转、ADL 和链上流程分别定义状态、持久证据、重试预算和结束条件。

每个连接器声明真实幂等身份及未知结果查询能力；不能假定所有动作都有客户端订单号，或请求超时即可按失败重发。链上流程还须处理 nonce、替换、确认及重组。数据库锁和本地 fence 只能限制受管理程序，账户接管仍须证明旧进程不能继续出站。

意图可携带版本化守卫条件；最终授权依据由执行器重新核验。开仓、减险、划转分别定义条件，策略暂停不等于停止已发送订单核对，也不隐式改变 ADL 与保证金管理各自的运行意图。

Python 过渡按账户执行权划界：

- 未接管的模块保留原执行器、原库及现有账户保护；新系统只读或模拟，不删除旧归属协议。
- 接管后，该账户只有新 executor 能发起资金写入。Python 若继续参与，只读快照并提交候选意图，不再直接签名下单或写新权威业务表。
- 发送前重算的守卫、逐批现场核对和多步恢复必须明确归属；不能把这些逻辑压缩成一次不可复核的“策略已批准”。
- 旧任务未决或无法可靠导入时，延后该账户及关联跨账户策略的切换。完整移植、恢复验证和唯一写者交接完成后，才能退役对应旧执行路径。

**保留 Python 策略不能掩盖执行迁移的实际成本。** 按前述接管规则，交易所接入、签名、订单与划转状态机、未知结果恢复和业务写入需要纳入新 executor 的统一归属。ASTER 交易目录的非测试 Python 约 1.8 万行；附录列出的保证金、ADL、开仓三类纯规划函数样例合计约两百行，不代表已经穷尽所有可复用逻辑。划转、ADL 和单腿补偿在动作中途还会重读交易所，不能把这些完整流程简化为一次“先判断、后执行”。若阶段 2b 最终选择由 TypeScript 实现上述执行职责，接管 ASTER 将涉及较大范围移植，应按职责和恢复案例盘点，而不是仅计算纯规划函数。Greeks 也需核对订单、RFQ 和对账状态机的迁移成本。

这一重写成本来自本方案选择由 TypeScript 新 executor 承接这些职责，不是唯一账户写入权在技术上必然要求同一种语言。阶段 2b 同时核验职责拆分、移植成本与语言边界；在选定该实现路径后，逐模块决定何时整体接管。尚未具备迁移条件的模块继续保留旧执行路径，不能让新旧执行器分别控制同一账户的部分资金操作。

### 5.4 账本与收益口径

成交、手续费、资金费、划转、外部现金流和估值分别保存，保留交易所原始值、归属、时间范围与读取完整性。事实记录与派生估值分离；实际仓位、策略归属及外部手工交易分别表达。

保留现有“资产变化”和“出金调整后的资产变化”指标。现有 Asset 的余额差分未完整剔除入金，不能称为投资收益；仅入金而无交易盈利的验收案例，收益不得增加。

投资净收益金额只有在统计账户集合、期初期末估值、外部现金流与计价换算完整时才能计算。同一边界内的净收益为期末权益减期初权益、减外部入金、加外部出金；现金流按发生时点换算，汇兑影响明确标注。平台内部账户间划转在平台总口径抵消，手续费单独记录，已反映在权益中的费用不重复扣减。无法解释的差额显示为“未解释资产变化”，不补零。收益率另行固定现金流时点和资本基数，不能把净收益金额直接除以任意余额。

原始流水从接入日起按既定保留策略持续积累。交易所回看窗口之外的历史通过报告导入并保留来源，不能将近期有界成交缓存当成全历史账本。逐账户、币种和截止时点对账；历史缺口、迟到成交和修正保持可追踪。旧研究报告保留原会话、模型与假设，不用新公式覆盖旧结果。

### 5.5 业务事件与可恢复消费

任务、规则变更及必要业务事件在同一业务库事务中保存。通知投递、账本投影和需恢复的页面事件逐个登记消费者、水位、重放范围、去重身份及清理条件。

事件允许重投，消费者按持久身份幂等处理；源事务和“事件已处理”记录的边界必须明确。外部通知响应丢失保留投递结果未知，不能因使用 outbox 就承诺外部恰好一次。页面游标超出保留范围时返回完整快照。

实时盘口不逐 tick 写业务事件表。研究历史的持久化、丢失与保留规则独立登记，不能因与交易事件分离就视为可丢缓存。

## 6 存储、凭据与前置验证

### 6.1 物理分库与数据保留

首期 SQLite 原型使用业务库和行情与历史库。**物理位置不决定是否备份**；每张表及每类文件登记拥有者、数据性质、保留期限、重建来源、备份方式和恢复依赖。

| 数据性质 | 典型内容 | 默认处理 |
| --- | --- | --- |
| 业务权威记录 | 账户、配置、订单、任务、流水、事件、水位、研究会话与模型参数 | 按业务保留策略备份；未知操作及恢复依赖不能按普通历史清理 |
| 不可重采观测 | 本地历史盘口组合、行情质量与缺口、盯市采样、研究原始样本 | 在约定保留期内备份或经验证的归档；不可宣称重新拉取当前行情可恢复 |
| 可重拉缓存 | 当前目录、最新快照、具有完整重取来源的派生结果 | 登记失效条件和重建成本后可排除备份；恢复期间显示缺失而非零值 |

业务权威记录默认放业务库；行情与历史库可同时含不可重采观测和缓存。Monitor 的 market_observations、quality_samples 不能整库按缓存排除。研究相关文件的清单同时保存样本范围、缺口、来源时间、会话配置、模型版本和报告引用。

首版优先备份包含保留观测的完整数据库及相关文件。只有独立归档经过内容校验和恢复演练，并在备份清单保留引用之后，才允许移出日常快照。保留期限到期是明确的数据政策，不等于数据本来可重建；迁移默认保留旧系统尚在保留范围内的历史。

### 6.2 写入归属与事务

| 写入者 | 可提交的内容 | 生效边界 |
| --- | --- | --- |
| api | 会话、普通界面配置；交易配置的候选版本、幂等命令 | 普通配置短事务生效；交易命令只有 executor 持久应用后才显示“已生效” |
| executor | 生效的交易规则、凭据绑定版本、暂停与接管状态、任务、订单、预占、核对结果、权威流水与事件 | 唯一业务写入入口，校验账户归属、任务及配置版本 |
| feeds / jobs | 所属采样、缓存及待导入材料 | 权威入账经版本化接口交给对应写者，不能直接覆盖执行表 |

候选配置只是请求，不直接修改当前交易现场。撤销、暂停等命令具有可查询的持久身份；页面显示“已受理/生效中/已生效/失败”，API 不把提交候选版本等同于停止交易成功。凭据轮换先持久撤销旧运行意图，再激活新绑定版本。

executor 在事务外读取网络和计算；进入短事务后重新比较配置版本、任务版本、账户写者代次，原子保存状态、预占和必要事件。版本变化即丢弃旧计算结果并重新读取。事务内不等待网络、不运行整段回放、不嵌套打开会提前提交外层事务的连接上下文；事务提交后仍执行最终发送守卫。

feeds/jobs 递交流水或回填结果使用稳定来源身份和有界批次。写者落盘后才确认，确认丢失可按同一身份重投；源端只有获得持久确认才推进水位。超出交易所重取窗口的材料先保存在纳入恢复清单的导入文件中，不能依赖内存队列保存唯一副本。大段回填分批调度，为执行和减险操作保留处理预算。

api 与 executor 即使写不同表，仍会争用业务库写锁。事务时长、锁等待、队列长度、checkpoint 和事件循环延迟都要记录。同步数据库调用必要时放入专属存储 worker；只有提交确认后才允许外部副作用，不能用异步尽力落盘换取较低延迟。

### 6.3 凭据与迁移

统一的是凭据管理接口、密文格式与轮换规则，不是为同一账户只保留一份 API Key。一个账户可以有只读、交易或不同权限范围的凭据；合并时核对主体、环境、用途、权限和密钥版本，不能直接按模块优先级“三选一”。密钥材料不进入前端和业务日志，备份能够恢复所需历史密钥版本。

各物理库有明确迁移拥有者和有序版本链，统一记录 SQL 哈希、支持的读写版本和备份清单版本。应用回滚只选择经过兼容性验证的版本；先扩后收并不能自动保证任意上一版本可回滚。跨库迁移用持久迁移记录组织，备份与切换核对一致检查点，不把两个 WAL 数据库当作一个原子事务。

### 6.4 存储与时序的阶段门槛

阶段 0 先登记代表性账户数、合约数、数据规模、回填量、运行设备及执行/通知/恢复预算。现有 1500 毫秒窗口与 ASTER 的采样周期仅是基线约束，不是新系统已经达到的性能承诺。

预算登记以旧系统现行常量为起始值，阶段 0 逐项确认保留、收紧或放宽并写明依据：

| 预算项 | 起始值 | 来源 |

阶段 1 至 2b 使用同一固定版本混合运行：API 配置保存、执行落盘、流水回填、长查询、备份和 checkpoint。检查写锁等待分布及最大值、事务持有时间、事件循环延迟、队列积压、实际发送时的数据年龄，以及中断后的记录完整性。

通过条件是：代表性负载下满足预先登记的预算；旧配置或失去写入权的结果不提交；超时有界且不会导致重复副作用；新鲜度不合格时明确拒绝，不能靠放宽阈值“通过”压测。若未满足，先定位事务/查询/存储调用问题；经过有界修正仍不满足时，在批量迁移前完成 PostgreSQL 方案验证与选择。保留原始测量结果，不用单个平均值代替执行时效证据。

阶段 1 起每批带部署骨架和恢复检查。阶段 2a 用最小界面承载完整交互；在扩大页面和语言迁移之前解决最关键的不确定性。ASTER 抢额度的时序原型在阶段 2b 评估，不能等到大量策略移植后才开始测量。阶段 2b 未通过时，先回到设计，不进入阶段 4 之后的批量工作。

策略新旧比较默认使用同一录制输入、只读影子或模拟执行。比较的是明确的契约和可解释差异，不能让新旧执行器同时操作同一真实账户。实盘金丝雀是未来账户接管前的单独执行步骤，需明确账户、额度、权限和当次授权；本次文档修订不执行实盘。

阶段 0 完成后按业务切片和未知项估算工作量，包含数据迁移、恢复和运行验证。附录 A.2 的行数可帮助盘点，但不能直接折算状态机移植时间，也不把“全部改写为 TypeScript”当作功能完成指标。

## 8 账户接管、回退与旧系统保留

1. 新系统先只读或模拟，对照仓位、流水、行情、预览和策略判断；同时记录数据时间与覆盖差异。
2. 按真实账户写入范围选择批次。多账户策略整体交接；同一账户涉及多个模块时一并核对执行归属。
3. 持久停止旧系统新的运行意图，处理或保留在途操作，证明旧写者已经退出且不能继续出站，再导入最终状态。
4. 校验原订单身份、未知记录、凭据绑定和配置版本后，才激活新写者。租约过期或旧页面关闭不能单独证明交接完成。
5. 未知任务不能可靠接管时，由原执行器继续核对，该账户不切换；不能以清空日志、创建新账户身份或重置保护库解除阻塞。
6. 新系统产生交易后，回退要交接新订单、流水和控制状态，重新建立唯一写者。旧程序不能读取新数据或恢复未决任务时，保持交易关闭并修复前进；不使用旧备份覆盖新成交。

旧程序及原始历史保留到对应账户的接管、回退和数据核对完成。新应用构建目录与业务数据目录分离；退役步骤只处理已完成交接的组件，不删除其他仍在运行的模块数据。现有账户保护及恢复协议在迁移期继续有效，不能先移除再补保护。

## 9 部署与验收

正式包由 CI 构建并固定提交与摘要。一条命令自动完成需要的依赖、配置、服务注册和启动；重复执行按内容与环境版本增量更新，保留配置和数据。无变化快速结束，只重启受影响进程，并说明更新和跳过的内容。

先准备、校验，再激活。API 可以单独更新，执行进程自身升级仍需受控停机或交接。候选入口的健康检查不能触发真实交易。数据库迁移、密钥版本与运行包兼容性共同决定可回滚版本；回滚程序不等于回滚业务事实。

验证按阶段实际影响选择：账户与合约契约、金额/现金流、执行失败路径、持续采集、订阅背压、存储争用、通知投递、升级及备份恢复。恢复演练既核对数据和密钥完整性，也核对持久未知操作、旧源状态与唯一写者；归档恢复失败不能静默显示完整历史。

Windows 原生工具验证适用的逻辑、类型和界面路径，systemd、权限及安装激活在既有非 WSL Linux CI 或明确指定的 Linux 环境验证。真实资金操作和服务器部署按当次授权执行。测试夹具通过、代码接入、正式发布与生产验收分别记录。

本稿属于纯文档变更：检查引用、结论、阶段依赖和提交门禁即可，不为方案修订机械运行代码全量测试或发布运行时版本；仓库的[文档工作流](../.github/workflows/docs.yml)对此类提交不生成发布候选。

- 各模块实际凭据存储、权限组合和轮换依赖；源码配置入口不等于用户服务器实际保存方式。
- 现有功能的实盘验收覆盖。功能矩阵记录代码、离线测试、测试环境、实盘证据，不能相互替代。

## 11 与现有演进计划的关系

[技术与架构演进](evolution-plan.md)继续约束旧系统。本文对执行器和业务权威库推荐同仓独立建设，允许重新设计领域、数据模型和进程接口；原地演进的部分（阶段 1、3）属于对旧系统的修改，按演进计划的契约与审查等级执行；不能将旧系统“近期保持模块边界不变”直接作为新平台的限制，也不能用新方案提前取消旧系统维护。

旧系统继续使用现有迁移链及保护协议。新系统的版本链和导入工具独立设计；旧系统 E1c-2 是否实施，由旧系统实际结构变更决定，不因文档发布自动并入或取消。

复用横向经验时核验现源码和适用条件。接口契约、交易所规则、金额精度、未知结果、恢复、部署等可作为回归资产；具体参数和历史测试名不自动成为新系统固定实现。业务事件的消费者在阶段 0 至 2b 按第 5.5 节明确后再接入。
