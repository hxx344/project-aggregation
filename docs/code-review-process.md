# 代码审查流程

判定标准见 [代码审查标准](code-review-standard.md)，逐项检查见 [清单](code-review-checklist.md)。本文件只规定**步骤、时限与留痕**。

```
定级 → 变更前对齐 → 自审 → 发起审查 → 独立审查 → 修复复核 → 合并门槛 → 合并后观察
                                    ↑__________________|
```

## 0. 定级

改动开始时先按标准第 3 节定为 R1/R2/R3，写在 PR 描述首行。定级决定审查深度与时限，不决定要不要审。

## 1. 变更前对齐（R3 必做，R2 建议）

在写代码前写清四件事，避免返工：

1. 要改变的用户可见行为是什么。
2. 影响面：哪些模块、接口、页面、部署路径会变。
3. 失败时会怎样，怎么回滚。
4. 哪些是本次不做、需要单独登记的。

R3 改动若方案本身有分歧，先对齐方案再写实现；不要在审查阶段推翻设计。

## 2. 提交前自审

作者（人或代理）在发起审查前完成：

1. 跑 `pnpm run check`，跑改动相关的测试（不是全部，也不是不跑）。
2. 过一遍 [清单](code-review-checklist.md)，不适用的注明原因。
3. 自查 diff：有没有夹带、调试残留、被放宽的断言。
4. 准备证据：**运行了什么、结果如何、什么没运行及原因**。

留痕格式（写在 PR 描述或提交信息）：

```text
风险等级：R2
已运行：pnpm run check；node --test tests/trading-pnl-pairs.test.mjs（12 passed）
未运行：浏览器交互测试（本机未起服务，CI 覆盖）
待确认：coverage 补录后是否需要主动失效缓存
```

「引用已有测试」不能写成「已验证」。

## 3. 发起审查

PR 必须包含：

- 风险等级与一句话目标
- 改动范围（按目录列出）
- 自审证据（上节格式）
- 回滚方式（R2 以上）
- 需要审查者重点看的地方（例如"这里改了缓存失效条件"）
- 关联的经验条目或 issue

大改动按模块拆成可独立审查的 PR。单个 PR 超过约 800 行时，在描述里列出模块覆盖清单，逐模块确认审查完成，不按行数跳过。

## 4. 独立审查

**顺序**（不要一上来抠细节）：

1. **意图与范围**：这个改动要解决什么，范围对不对，有没有该一起改而没改的同类路径。
2. **语义与正确性**：按标准 D1–D2 看数据、状态、缓存。
3. **失败路径**：D3，超时、重试、部分失败、清理。
4. **安全与交付**：D4–D5，R3 必看。
5. **证据与卫生**：D6–D7。
6. 最后才是可读性。

**时限**（工作日）：R1 半天内首轮，R2 一个工作日内，R3 两个工作日内。超时未审视为阻塞，由合并者决定是否升级处理，不允许"等不及就先合"。

**意见格式**，一条一议：

```text
[P1] server/trading-pnl.mjs:120
问题：收益在写入时预计算，补录 coverage 后读取仍返回旧值
触发：record() 之后补录 funding coverage
后果：页面显示过期收益，用户按错误收益决策
依据：L002
建议：读取时按当前 events/coverage 重算；若要缓存，补失效条件
```

要求：

- 每条给级别、位置、触发条件、后果、建议。
- 没有复现路径的判断标「待核实」，不按 P1 阻塞。
- 同一根因的多个位置合并为一条，列出全部受影响位置，不刷条数。
- 不确定是否属于本次范围的问题，标「范围外」并单独登记，不混进阻断项。

## 5. 修复与复核

- 作者逐条回应：修复 / 拒绝并说明理由 / 转为 P2 登记。
- 复核只看**增量 diff 与关联面**，不重开全量审查。
- 同一 PR 的审查轮次上限 3 轮。第 3 轮仍有 P0/P1，说明方案有问题：停下来重新对齐设计，不要继续打补丁。
- 修复引入新逻辑时，按新改动重新定级，不能沿用原级别的宽松标准。

## 6. 合并门槛

合并者逐项核对标准第 6 节。任何一项不满足都不合并，包括：

- CI 红或跳过了相关 job
- 有未关闭的 P0/P1
- 自审证据缺失或与 diff 不符
- R3 没有独立审查记录
- 夹带无关改动

合并方式：保持提交历史可追溯，不把多个不相关改动压成一个提交。

## 7. 合并后

- 观察真实入口：至少确认一次用户实际路径可用，不只看 CI 绿。
- 合并后发现的 P0/P1 记为**逃逸缺陷**，回填到下次复盘，并检查清单是否缺项。
- 与 [daily-review-prompt.md](../daily-review-prompt.md) 衔接：复盘审的是已合入历史，不替代本流程；本流程的审查记录可作为复盘证据。

## 8. 热修通道

仅限线上已出现的 P0（资金、越权、不可用）。条件：

1. 改动最小化，只修该缺陷，不夹带重构。
2. 合并后 24 小时内补一次完整审查，并在 PR 中标注「热修补审」。
3. 补审发现的遗留问题按正常流程登记，不因为"已经上线"而降级。

## 9. AI 代理参与规则

- 代理可以作为**作者**，也可以作为**审查者**，但同一改动不能既当作者又当唯一审查者。
- 审查代理只读：不改代码、不提交、不合并，只输出带证据的意见。
- 审查代理的上下文应与作者隔离：只给仓库、改动范围、标准与清单，不给作者的结论与自评。
- 代理的「已验证」必须对应真实执行过的命令与输出；无法执行时明确写「未运行」。
- 代理发现的问题若属于新的缺陷类别，按 [AGENTS.md](../AGENTS.md) 记录事件；不因审查而批量新增经验条目。

### 让不同客户端都遵守

规则只在**被加载**时生效。各客户端读取的入口不同，因此仓库根目录 `AGENTS.md` 是唯一权威，其余文件只是入口：

| 客户端 | 读取的文件 | 说明 |
| --- | --- | --- |
| Codex CLI | `AGENTS.md` | 从根目录向下逐级合并，子目录可用 `AGENTS.override.md` 覆盖 |
| Claude Code | `CLAUDE.md` | 已 `@AGENTS.md` 导入，无需额外配置 |
| DeepSeek（经 Cline / Roo / aider 等） | `.clinerules`、`.roo/rules/`、`CONVENTIONS.md` | 模型本身不带配置，取决于客户端；`.aider.conf.yml` 已声明自动读取 `CONVENTIONS.md` |
| Cursor | `.cursor/rules/project.mdc` | 旧版 `.cursorrules` 仍保留兼容 |
| GitHub Copilot | `.github/copilot-instructions.md`、`.github/instructions/` | 按 `applyTo` 生效 |

这些入口文件只写"读 `AGENTS.md` 的哪一节"，不复制规则正文；规则变更只改 `AGENTS.md` 一处。

**机器门禁**（不依赖模型自觉）：

```bash
node scripts/review-gate.mjs --staged                  # 提交前
node scripts/review-gate.mjs --range origin/main...HEAD  # PR
```

只检查新增行：调试残留、`.only`、未解决冲突、疑似凭据、禁止提交的目录。启用预提交钩子：

```bash
git config core.hooksPath .githooks
```

钩子已由 `pnpm install` 的 `prepare`（`scripts/install-hooks.mjs`）自动启用，无需手工配置。两条钩子分工：

| 钩子 | 检查 | 失败后果 |
| --- | --- | --- |
| `pre-commit` | 新增行的内容问题 | 提交被拒，指出文件与行号 |
| `commit-msg` | 改动涉及 `src/`、`server/`、`modules/*/src/`、`deploy/` 时，提交信息须含「风险等级」与「已运行/未运行」 | 提交被拒，打印证据模板 |

门禁只覆盖可机械判定的部分。语义、缓存、资金边界和证据**内容是否真实**仍须按清单人工确认——**不要因为门禁变绿就认为审查完成**，也不要为了过钩子而填写未实际运行的检查。

**没有斜杠命令的客户端**，直接把下面这段作为审查指令：

```text
只读审查当前改动，不修改文件。先读 AGENTS.md、docs/code-review-standard.md、
docs/code-review-checklist.md。用 git status / git diff 确认范围，范围不清先问。
按标准第 3 节定级，按 D1–D7 顺序审查，先语义后细节。每条意见给出
[P0-P3] 文件:行、触发条件、后果、依据、建议；无法复现的标"待核实"。
最后给出是否满足合并门槛、P0/P1 数量、未覆盖的检查。
```


## 10. 度量

只跟踪能反映质量的指标，不统计评论条数或审查时长排名。

| 指标 | 含义 | 目标方向 |
| --- | --- | --- |
| 逃逸缺陷数 | 合并后发现的 P0/P1 | 下降（主指标） |
| 首轮发现率 | 首轮审查即发现的 P0/P1 占比 | 上升 |
| 平均审查轮次 | 每个 PR 的审查轮次 | 下降至 1–2 |
| P2 积压 | 登记未处理的 P2 数量 | 有界，不无限增长 |

每季度（或每 20 个 PR）看一次：逃逸缺陷集中在哪个维度，就补该维度的清单项或测试；指标没有改善时，先怀疑流程执行不到位，而不是加更多检查项。
