# 部署说明

## 总部署入口

推荐使用 [README 的一键命令](../README.md#一键部署五个模块与平台)，运行本仓库 `install-all.sh`，一次安装或更新五个模块与平台。原 `install.sh` 继续只管理工作台，兼容已有用法。

完整总部署支持 Ubuntu 24.04、Debian 12/13 的 x64/arm64 systemd 主机；Ubuntu 22.04 默认 Python 不满足 Variational 要求，可选择仅更新其余模块。首次安装自动创建各项目的默认配置和独立登录凭据，无需逐个运行安装命令。已有配置、端口、密码和数据库由各项目原安装器保留；工作台的项目登录凭据仍需首次在“项目管理”保存。总部署不会自动设置交易所 API Key、实盘开关或项目间的数据源凭据。

| 环节 | 执行规则 |
| --- | --- |
| 系统依赖 | 下载命令需要已有 curl 和 CA 证书；极简新系统缺少时按 README 补齐一次。安装器按所选项目合并其他缺失包，一次更新包索引并安装；全部存在时跳过 apt。 |
| 安装器准备 | 最多并发三个 HTTPS 下载；ETag 条件请求、SHA-256 本地完整性检查及 Bash 语法检查。五项全部准备成功后才开始应用部署。网络或校验失败不会使用过期脚本继续。 |
| 应用部署 | ASTER → Monitor → Asset → CrossEx → 工作台，串行执行构建及服务切换，降低峰值资源占用；未选项目不执行。 |
| 增量更新 | 每次调用原安装器，依照各自源码、配置、运行环境、缓存和健康状态决定更新或跳过。总部署成功记录不替代实际检查。 |
| 失败重试 | 当前安装器按自己的规则恢复，后续项目不执行，之前成功的项目保留。修复后重复原命令，重新检查所选项目。 |
| 中断 | 转发终止信号给当前安装器并等待其退出，让它完成自己的恢复流程，再释放总部署锁。 |

下载的安装器副本在本次执行期间固定，内容摘要记录在日志目录的 `项目.sha256` 中；子安装器仍独立获取各自 `main` 的应用源码。这不是六仓库的统一源码版本锁定，也不提供跨项目整体回滚。各项目继续独立维护 Node 运行时、依赖、构建结果和回退版本，升级不迁移这些目录。文档改动是否触发应用构建仍取决于对应项目的现有安装器。

参数：`--only aster,monitor,asset,crossex,variational,hub` 选择项目，顺序仍由依赖顺序决定；例如 `--only monitor,crossex,hub`。此选项不会自动补选其他模块，选定项目继续使用已有连接配置。`--refresh` 强制重新获取安装器，仅影响小脚本缓存；`--help` 查看用法。通过管道下载执行时，参数放在 `sudo bash -s --` 后；已有脚本文件时直接执行 `sudo bash install-all.sh`，下载方式见 README。

安装器缓存位于 `/var/cache/project-aggregation-stack/`，日志位于 `/var/log/project-aggregation-stack/时间.随机串/`，目录为 0700，文件为 0600，只允许 root 访问；日志可能含原安装器输出的首次密码。每个模块的完整输出保存为 `aster.log` 等，并实时显示到终端；终端输出中断不会破坏磁盘日志或提前终止正在切换服务的安装器。`summary.txt` 记录每项结果和耗时。下载或执行失败时，日志及已验证缓存继续保留，失败下载不会覆盖此前可用缓存。每次运行的日志单独保存，不清理项目数据。

总部署通过 `/run/lock/project-aggregation-stack.lock` 防止自身重复执行，子安装器继续使用各自部署锁。模块锁冲突时按照失败处理，修复后重跑。总结中的“完成检查/部署”表示该安装器成功退出；实际更新和跳过的环节见对应日志，不能据此认定各模块已经互相连接或行情已更新。

Variational Grid 使用独立安装器 `hxx344/variational-grid/main/install.sh`，总部署名称为 `variational`，不传策略切换参数。它要求 Python 3.11+；Ubuntu 22.04 默认环境选择此模块会在所有安装操作之前失败，可使用 `--only aster,monitor,asset,crossex,hub` 跳过。首次安装/会话失效需要交互式 SSH 终端；总部署在 setsid 前打开终端并仅传入标准输入，Python getpass 隐藏输入，token 不放入命令参数、环境变量或日志。无终端时预检已有会话，不能验证则提前退出。

旧 Variational 仓库地址只在匹配已知旧地址时迁移；原配置、账本、服务名和已选模式继续保留。其页面 `127.0.0.1:9876` 通过工作台授权代理，不需工作台保存行情 token。升级工作台一次性添加 `variational`，同标识已有配置和用户删除决定保留。摘要仅显示独立模拟结果，不纳入资产账本。

## 目录与更新行为

安装器仅管理 `/opt/project-aggregation` 内自己标记的程序版本及固定名称的 systemd 服务。初次发现非空且没有管理标记的目录或同名未知服务时停止，不覆盖现有内容。

每次更新先查询 `main` 的提交，再比较配置、运行环境、依赖锁和代码内容。无变化且健康时直接退出；文件变更只重新执行对应环节：

| 变化 | 执行内容 |
| --- | --- |
| 没有变化、服务健康 | 不下载源码，不装依赖，不验证，不构建，不重启。 |
| 仅 README / docs 等文档 | 获取新提交后确认应用内容相同，不重建或重启。 |
| 服务配置 | 复用依赖、验证与构建结果，更新服务并检查健康。 |
| 后端代码 / 测试 | 重新验证；前端无变化时复用前端产物。 |
| 前端代码 | 重新验证并构建。 |
| 依赖或 Node / npm 环境 | 建立新的依赖缓存，重新验证并构建。 |

依赖安装和项目脚本均以专用服务用户运行。验证通过后使用原子符号链接替换激活版本，重启后轮询 `/api/health`。激活前保留上次成功的环境配置；失败时先把本次配置保存为 `/etc/project-aggregation.env.failed-时间-PID`，再原子恢复旧环境文件、旧程序指针和旧 systemd 配置，并改用上次成功的 HOST / PORT 重启和检查旧服务。成功环境快照位于 `/opt/project-aggregation/.last-successful.env`，只在健康检查成功或确认配置指纹未变且健康时更新；快照及失败候选均为 root 的 0600 文件。首次安装失败不会覆盖用户配置；已有部署缺少可信成功快照时会在激活前停止，避免丢失仍运行的服务。持久数据库保持原样；未来若新增不兼容数据迁移，必须先实现迁移备份与兼容回退，不能仅依赖程序回滚。

成功后保留当前及前一个版本，清理只针对安装器标记且路径满足约束的旧版本。可重复利用的依赖、构建缓存保留；失败工作目录保留用于排查，不删除用户未知目录。

单独使用工作台 `install.sh` 不会修改或重启服务器上的 3000、3200、5678、8765、9876 原项目服务。健康检查只确认工作台可响应，不证明原项目已连接或数据新鲜。五个模块和平台的连续安装或更新使用上方总部署入口。

## 浏览器入口与服务器接口

工作台与五个项目部署在同一台服务器时，服务器直接访问 `127.0.0.1:3000`（monitor）、`127.0.0.1:3200`（CrossEx）、`127.0.0.1:5678`（Asset）、`127.0.0.1:8765`（ASTER）和 `127.0.0.1:9876`（Variational）。电脑只需转发工作台的 `3100`：

```bash
ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:3100:127.0.0.1:3100 user@server
```

把 `user@server` 替换为服务器登录地址并保持终端运行。浏览器打开 `http://127.0.0.1:3100` 后跳转到 `http://hub.localhost:3100`。在工作台打开项目时，会进入该项目独立的 `.localhost` 子域，端口仍为 `3100`。Chrome / Edge 自动把这些名称解析到本机，无需配置 hosts 或 DNS；当前不承诺 Safari 支持。[浏览器兼容说明](https://learn.microsoft.com/en-us/aspnet/core/test/localhost-tld?view=aspnetcore-10.0)

点击左侧项目会直接显示原始页面，无需先进入摘要页或再点“载入”。内容区保留原项目功能，支持重新载入、单独打开和连接设置；总览仍提供摘要。升级无需修改旧 `mode` 设置，摘要刷新不会打断原页面操作。

三个内置项目默认使用 `accessMode=proxy`，旧记录缺少该字段时也使用此默认值。代理目标仅由 `apiUrl` 决定；`url` 提供页面入口路径及查询参数，因此 monitor 的 `?monitor=oil` 等参数会保留。选择 `direct` 时浏览器直接打开 `url`，该地址需自行可达；`standard` 和 `link` 默认使用 `direct`，也可配置接口地址后改为 `proxy`。

CrossEx 的第四预置入口使用标准接口，但显式设为 `proxy`。在“项目管理”填写用户名 `admin` 和 CrossEx 独立密码（首次启动在 `sudo journalctl -u gate-crossex-arbitrage --no-pager -n 30` 查看），即可复用标准接口预检与代理自动登录。进入 CrossEx 页面后配置 Monitor 数据源及来源凭据；工作台不会代填。第一版仅执行模拟，模拟余额不计入工作台真实资产。

升级只会一次性补充缺失的 `crossex` 入口，不覆盖已有配置；手动删除后重启不重加。已满 30 个项目时跳过补充并标记完成，需腾出名额后手动新增。该迁移仅增加项目及设置行，旧版仍可读取，程序回滚不删除已有项目。

新实例预置 ASTER 页面与接口地址为 `http://127.0.0.1:8765`。升级不改写旧接口地址；现有项目若误填为 `http://127.0.0.1:18765`，应在“项目管理”改为 `http://127.0.0.1:8765`，重新输入 ASTER 网页登录密码并保存。工作台不会自动换端口或搬用旧密码。代理模式不使用旧页面地址的主机与端口作为目标。

在“项目管理”保存原项目登录凭据后，通过工作台打开 ASTER、Asset 和 monitor 即可自动登录。每次 ASTER / Asset 页面授权建立独立的原项目会话，不与后台读取及同步共用；monitor 用保存的 Basic 凭据预检 `/api/monitors`。`standard` 采用 `proxy` 时，以已有的 `/api/hub/summary` 预检 Basic 凭据。密码、Basic 认证信息和上游会话只留在服务器，浏览器只持有工作台的页面授权 Cookie。

没有保存凭据时，仍可在原站登录，也可回“项目管理”保存一次。登录失败或会话过期时，回工作台重新打开项目；原站密码变更后需更新保存的信息。`direct` 和 `link` 项目仍自行登录原站。在原项目退出会撤销当前页面授权；退出工作台会撤销全部页面授权，修改项目配置也会撤销该项目已有授权。

工作台通过一次性票据授予页面访问，随后使用绑定工作台会话和独立项目主机的 host-only Cookie。代理将原页面的嵌入限制调整为仅允许当前工作台，保留其余 CSP；原页面的根路径、登录跳转和 monitor 实时流通过代理保留。

## Asset 后台同步

启用项目的 `autoSync` 并保存原项目登录凭据后，工作台服务器每 60 秒调用 Asset 的 `POST /api/sync`，不依赖浏览器、原页面或 SSH 连接是否保持打开。旧 Asset 配置缺少此字段时默认开启，其他适配器默认关闭；项目设置可随时开关。普通摘要仍每 30 秒读取 `GET /api/ledger`，单次同步最多等待 60 秒，不阻塞其他项目读取。

同步会更新原资产项目的估值及历史，不执行下单或转账。后台同步状态与源数据时间分别展示；上游部分来源失败时可能仍返回账本，因此同步请求完成不表示所有来源已更新。失败保留上次数据与真实时间。关闭后台同步后，账本摘要读取和原页面自己的同步功能继续按各自设置运行。

通过工作台打开 Asset 原页面时，已开启后台同步且已保存密码的 `/api/sync` 请求与后台共用一次同步。代理使用当前页面授权保存在服务器上的 Asset 会话，先验证账本访问权限，同步完成后再读取真实账本，避免同时刷新造成锁冲突；不要求浏览器持有原站会话 Cookie。页面授权或上游认证无效时不能读取，同步失败不伪装为成功。关闭后台同步后，原页面同步请求照常转发。

## 可选 HTTPS 反向代理

如果服务器已经有 nginx 和证书，可用以下 server 块提供工作台 HTTPS 入口，替换域名与证书路径。首次使用可直接采用上述 SSH 转发，工作台无需公开监听。

```nginx
server {
    listen 443 ssl;
    server_name hub.example.com;
    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:3100;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_read_timeout 30s;
    }
}
```

在 `/etc/project-aggregation.env` 中添加以下无引号配置，然后重跑安装命令：

```dotenv
PUBLIC_ORIGIN=https://hub.example.com
COOKIE_SECURE=true
```

`PUBLIC_ORIGIN` 将这个完整来源加入工作台允许入口，保留外部 `Host` 对来源检查是必要的。安装器保留该字段，并将环境文件整体纳入变更检测与失败恢复。工作台不直接信任任意客户端传入的 `X-Forwarded-Proto`，HTTPS Cookie 由配置确定。

这一配置只提供工作台 HTTPS 入口，不承诺在任意域名下代理完整原页面。单端口原页面代理当前以 SSH 和 `.localhost` 为支持方式；使用 HTTPS 工作台时，可将项目设为 `direct`，指向各项目已有的浏览器可达地址。嵌入仍受原页面安全策略及 HTTPS 混合内容规则影响。

## 验收范围

本地 Windows 可运行应用检查、构建和模拟上游测试；Git Bash 可做安装脚本语法检查。这些不替代 Linux 的服务安装验收。GitHub Actions 在 Windows Node 24.x、Ubuntu Node 24.15.0 和 24.x 上运行完整应用检查、测试及构建。独立 Ubuntu 安装检查覆盖脚本语法、路径边界、原子切换、模拟失败回滚，以及从 3100 改为冲突端口后恢复旧配置和旧健康检查地址的回归，不安装到真实生产服务器，也不读取真实项目凭据。

总部署使用 `bash deploy/test-all.sh` 做契约回归：首次执行、缓存命中、单脚本更新、缓存缺失/损坏、下载/语法失败保护、依赖合并安装、失败停止后续、重跑重新检查及模块选择。Windows 原生 Git Bash 使用模拟系统边界；Ubuntu Actions 额外验证真实进程组的信号转发、锁释放以及日志权限。测试不执行生产模块安装，也不使用 WSL。

服务器上的最终验收：只保留 3100 转发；工作台可登录，保存原项目凭据后五个原页面能自动登录、加载资源和操作；monitor 实时数据持续更新；CrossEx 配好 Monitor 来源后可读取发现结果并进行模拟，真实资产金额不受模拟余额影响；关闭 Asset 原页面后后台同步仍执行，状态与源时间分别显示；关闭后台同步后不再自动触发同步；原站退出使当前页面授权失效，工作台退出使全部页面授权失效；更新凭据后从工作台重新打开能恢复访问。重复运行安装命令确认显示跳过项，保存的配置与数据仍在。尚未连接目标服务器时，不应报告这些实机验收已经通过。

原页面入口的浏览器回归检查：保留旧 `mode=external` 配置，点击各代理项目应立即进入原页面；刷新总览时保留原页面未保存的输入；模拟一个入口请求挂起后切换项目，迟到响应不能替换当前页面；停用项目后不再签发页面入口；重新载入取得新的入口；手机宽度下内容区不出现横向溢出。直接访问项目仍按其 `mode` 选择新窗口入口或嵌入。
