# ASTER 首次打开等待优化

用户现象是点击 ASTER 后长时间显示“正在连接交易服务”，稍后可以进入。这句话已经包含在 ASTER 的首屏 HTML 中，前端脚本加载并完成水合之后才开始读取 `/api/state`。

ASTER 当前静态文件服务未启用压缩，工作台此前原样转发，因此首屏 788,858 字节的 JS/CSS 全部经过 SSH 转发。此次在工作台代理中为现有规则允许缓存的公开、不可变、带构建哈希的 JS/CSS 增加 gzip 流式传输，只需更新工作台。

## 本地限速结果

使用 Windows 原生 Node.js 24.15.0、Chromium、真实工作台及 ASTER 生产构建；测试上游按 ASTER 的实际 manifest 设置缓存头，原样发送未压缩资源。状态接口返回隔离的空账户测试数据，不连接交易所。每次使用新浏览器上下文和禁用缓存，网络设为下载 128 KiB/s、延迟 100 ms，从打开工作台 ASTER 地址计时，直到状态已读取并显示“添加账户以开始”。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 首次可用时间 | 8,399 ms | 4,337 ms |
| ASTER JS/CSS 传输正文 | 788,858 B | 300,539 B |
| 解码后 JS/CSS | 788,858 B | 788,858 B |
| 页面脚本异常 | 0 | 0 |

首屏静态传输量减少 61.9%。这是各一次冷加载的本地对照，并非线上耗时或稳定性保证。实际 CSS 未列入上游 immutable manifest，本次保持原样；小于 1 KiB 的文件也保持原样。仅四个较大的 JS 包启用压缩。

## 验证与边界

- Windows 原生 `npm test`：115 项通过；`npm run build` 包含类型检查并通过。
- 浏览器验证通过：总览预加载不读取交易状态；点击后读取；切回总览暂停；再进入复用原页面并恢复读取；手动重新载入后正常连接，页面脚本异常为零。
- 覆盖 gzip 解码一致性、浏览器拒绝压缩、HEAD、条件请求、已有压缩、Range、`no-transform`、私有响应及下载取消。
- gzip 使用背压与流式处理，不缓存代理正文；压缩后删除不再适用的长度、范围和摘要头，弱化 ETag，正确合并 `Vary: Accept-Encoding`。
- HTML、API、SSE、携带会话的响应以及未通过既有公开资源规则的文件不参与压缩；页面授权和交易处理逻辑不变。

未在用户服务器部署或测量；服务器登录需交互认证。服务器可通过总部署入口的 `--only hub` 更新工作台后重新加载页面。
