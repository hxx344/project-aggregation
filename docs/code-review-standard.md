# 代码审查标准

本文件规定单次改动**合并前**如何判定合格。它不重复 [LESSONS.md](../LESSONS.md) 的具体经验，只规定审查范围、定级、证据与判定门槛；具体检查项见 [审查清单](code-review-checklist.md)，执行步骤见 [审查流程](code-review-process.md)。

## 1. 适用范围

| 改动类型 | 审查方式 |
| --- | --- |
| `src/`、`server/`、`modules/*/`、`deploy/`、`scripts/`、`tests/`、配置与依赖 | 完整审查，按第 3 节分级 |
| 纯文档（`docs/`、`*.md`） | 轻量核对：结论准确、引用路径有效、不复制其他文件的规则正文 |
| 生成物（`dist/`、`output/`、构建产物） | 不审生成物本身，审生成源与产物一致性 |
| 依赖锁文件、CI 配置 | 按实际行为影响审查，不因"只是配置"跳过 |

与其他机制的分工：本文件管**单次改动**；[daily-review-prompt.md](../daily-review-prompt.md) 管**已合入历史**的增量复盘；[code-standards.md](code-standards.md) 管经验升级后的**强制规范**。三者不互相替代。

## 2. 角色与独立性

- **作者**（含 AI 代理）：完成自审、标注风险等级、提供可复核证据。
- **审查者**：不得只读 PR 描述就下结论，必须看 diff 与调用方。
- **合并者**：核对第 6 节门槛，不代替审查者做判断。

**单人例外**：本仓以单人开发为主，允许作者自审后合并，但须同时满足：

1. 走完 [审查清单](code-review-checklist.md) 并逐项留痕（勾选或注明不适用）。
2. R3 高风险改动（第 3 节）必须有一次**独立审查**：另起一个会话或代理，只给它改动范围与仓库，不给作者的结论；禁止复用作者的上下文自我确认。
3. 代码、配置与测试提交在提交信息保留自审证据；PR 可复用并补充独立审查记录，格式见 [流程](code-review-process.md#2-提交前自审)。

## 3. 改动分级

按**风险**分级，不按行数。行数只影响审查批次拆分。

| 等级 | 判定 | 典型范围 | 最低要求 |
| --- | --- | --- | --- |
| **R3 高风险** | 出错会直接造成资金、权限或不可逆后果 | 下单/平仓/杠杆/保证金、凭据与鉴权、特权更新器、部署激活与回滚、数据库结构与迁移、对外公共契约 | 独立审查 + 失败场景测试 + 回滚方案 |
| **R2 中风险** | 出错会静默产生错误数据或不可用 | 行情与持仓读取、缓存与失效、调度与恢复、跨模块调用、构建与依赖升级 | 自审 + 相关测试 + 证据 |
| **R1 低风险** | 影响局限于展示或文案 | 样式、文案、纯展示组件、补充单测、文档 | 自审；影响代码时做相应检查，纯文档核对引用与结论 |

分级存疑时按高一级处理。

## 4. 严重级别

| 级别 | 定义 | 处置 |
| --- | --- | --- |
| **P0 阻断** | 会造成资金/持仓/订单错误、凭据泄露、越权操作、数据损坏，或使部署无法回滚 | 必须修复，禁止合并 |
| **P1 阻断** | 会静默产生过期或错配数据、真实用户入口不可用、恢复无界、或声称验证但未执行 | 必须修复，禁止合并 |
| **P2 应修** | 不改变当前结果，但会放大后续缺陷：重复逻辑、错误处理不足、未测量的性能退化、测试缺口 | 可合并，须登记 issue 或同批修复 |
| **P3 建议** | 命名、注释、可读性、局部风格 | 不阻塞，作者可拒绝 |

**定级证据门槛**：P0/P1 必须给出「触发条件 + 代码位置 + 后果」三要素。无法给出复现路径的猜测只能标为**待核实**，不得按 P1 阻塞，也不得写成已修复。

## 5. 审查维度

每维给出必须回答的问题。括号内是同类问题在本仓的历史证据，用于判断"这不是假想风险"。

### D1 结果正确性与数据语义

- 计算用的单位、精度、计价币种是否与目标一致？（L016 稳定币法币换算、L038 十进制不重套输入长度）
- 标的、合约、账户的身份是否全程可区分，有没有在某一层被合并？（L020 标的与原生合约身份、L027 配对计价字段）
- 分子与分母是否描述同一口径？（L059 资本回报双腿头寸）
- 时间窗口、分页、全历史读取是否覆盖声称的范围？（L045、L047 首屏与完整历史契约）
- 聚合是否限定了可聚合的类型？（L025 账户流水按委托聚合）
- 成交/事件之后，读取到的现场是否**证明**已反映该事件，而不是"应该已经反映"？（L054）

### D2 状态、缓存与时效

- 缓存的读取语义是否等于当前计算语义？失效条件覆盖哪些更新？（L002）
- 展示调度周期是否被误当成数据有效期？（L040 调度周期不能延长快照有效期、L049 刷新要覆盖请求耗时与缓存剩余）
- 页面状态是否被当作服务端连接状态使用？（L058）
- 主动断开、主动停止后，哪些值应保留、哪些必须停止老化？（L056）
- 恢复事件（`visibilitychange`/`focus`/`pageshow`/网络恢复）是否合并，且不误取消本轮新请求？（L003）
- 配置迁移时，同值写入会不会覆盖新模型的细分选择？（L042）

### D3 失败路径与有界恢复

- 每个网络/磁盘/外部调用：超时、重试次数、退避、总时限是否明确且有界？（L013 自动/手动/重启后都受限、L050 短暂失败有限恢复）
- 部分失败时，已成功部分与已写入状态是否一致？重试是否幂等？
- 拒绝或失败的请求，前端提交标记是否解除？（L029）
- 异步清理顺序是否正确：先释放同步资源，再等待子任务？（L037）
- 断开、重连、卸载、切页时，定时器与订阅是否清理，会不会重复启动轮询链？

### D4 安全、权限与资金边界

- 特权操作的输入是否只来自可信来源，而不是请求体或前端可改字段？（L009）
- 凭据、token、账户标识是否可能进入日志、错误信息、响应或前端包？（L014 脱敏边界内保留可诊断性）
- 停服更新、批量操作前的"没有待处理订单"是否有完整且新鲜的依据？（L008）
- 越权路径：新增接口是否都经过与同类接口一致的鉴权，包括只读接口？
- 失败是否"默认拒绝"而不是"默认放行"？

### D5 真实入口与交付路径

- 改动是否在**用户实际使用的入口**上验证过，而不是只在开发服务器或测试桩上？（L017）
- 构建/安装实际读取的输入是否与提交内容一致？（L011 源码导入后的构建输入）
- 发布身份是否一致：运行内容相同不等于正式发布身份相同。（L015）
- 安装/更新脚本改动是否覆盖真实安装入口、临时目录、冻结安装与缓存目录？（L018、L019、L032、L055）
- 长时间操作是否可观测：进度、续传、失败诊断？（L030、L036）

### D6 验证与证据

- 新增/修改的测试是否覆盖**失败场景**，而不只是成功路径？
- 作者是否**实际运行**了相关检查？引用已有测试不等于运行过。
- 优化类改动是否有参考结果与规模检查，而不是只看"更快"？（L006、L007）
- 前后端对同一持久金额/条件的语法是否一致，并有测试同时覆盖两侧？（L044）

### D7 变更卫生

- 一个改动是否只做一件事？重构与行为变更是否分开？
- 拆分模块/改名后，所有调用方是否迁移完成？（L005）
- 是否有调试残留、临时开关、注释掉的代码、被放宽的断言？
- 依赖升级是否说明了影响面与回滚方式？
- 文档、`LESSONS.md`、`code-standards.md` 是否与实际行为一致？没有新证据不新增经验条目。

## 6. 合并门槛

全部满足才可合并：

1. 按影响范围选择的类型检查、相关测试与必要 CI 通过；纯文档不机械运行代码检查，本任务内输入与环境未变的有效结果直接复用。
2. P0、P1 为 0；P2 已登记（issue 或同一 PR 修复）。
3. R3 改动有独立审查记录与回滚方案。
4. 证据齐全：运行了什么、结果如何、什么没运行及原因。
5. 文档与经验库同步；不把未修缺陷描述为已修复。
6. 改动范围与 PR 描述一致，无夹带的无关修改。

## 7. 审查者不做的事

- 不因个人风格偏好定级；格式问题交给工具。
- 不把未核实的猜测写成缺陷结论。
- 不在审查中顺手重构作者代码（P0 修复除外）。
- 不因"以前就是这样"而放过同类问题——同类路径要么一起修，要么明确登记。
- 不要求低风险文案改动补充复述实现的测试。

## 8. 与经验库的闭环

审查中确认的缺陷，若属于可复用的类别，按 [AGENTS.md](../AGENTS.md) 记录事件（适用条件、根因、以后做法、验证、证据）。同一类别在不同日期重复出现，才按 [升级规则](code-standards.md#升级规则) 升级为强制规范。

审查发现的问题在合并后复发，按**逃逸缺陷**记录，并在下次复盘时检查审查清单是否需要补项。清单条目只能因为真实逃逸而增加，不因为"想更全面"而膨胀。
