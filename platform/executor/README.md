# 执行器原型（统一平台阶段 1–2）

统一交易与资产平台阶段 1 的首切片：原油 CLUSDT 在 Binance 与 Bybit 之间的跨所双腿开平仓，覆盖预览、确认、执行、核对、停止、超时、重启接管与故障注入。阶段 2 另有 ASTER 配对子账户保证金平衡划转的复杂恢复切片与 ASTER ADL 应急处理切片（均见“关键语义”）。方案见 `docs/unified-platform-plan.md` 与 `docs/unified-platform-phase0.md`，盘点与预算见 `docs/unified-platform-phase0-inventory.md`。

## 边界

- 默认只有进程内模拟场所。带 `--live-config` 启动为实盘金丝雀模式（3.0c，见“实盘金丝雀模式”）：只接 Binance、Bybit 两家真实下单连接器与名义金额上限，不接共享写者登记、ASTER 划转、ADL 与持仓展示。执行器拒绝混用：实盘环境只接受 `transport: 'live'` 的连接器，模拟环境只接受模拟传输；ASTER 三类连接器只接模拟（实盘留到阶段 3.3）。另有操作者手动运行的两个契约探测脚本（见“真实接口契约探测”），不属于执行器。
- 独立入口、独立数据目录 `executor.sqlite`；拒绝含 `hub.sqlite`、`execution-control.sqlite`、`credentials.key` 或 `modules` 的目录，不读写工作台数据。例外是工作台的原油金丝雀按钮（3.0d，见“工作台金丝雀按钮”）：它由工作台的接口实测页启动，读取交易中心保存的执行账户，并把执行器库放在工作台数据目录下的 `executor-canary`。
- 共享写者登记（`execution-control.sqlite` 协议，实现为 `server/execution/account-writer.mjs`）只能通过 `createExecutor({ control })` 注入；入口 `main.ts` 不接入，测试只用临时目录里的登记库；实盘环境注入登记直接拒绝启动（`control_mainnet`）。模拟传输下只允许以 `testnet` 或 `demo` 身份登记，因为登记会把账户永久钉选给首个认领的模块。
- 不在工作台发布包内（`deploy/package-release.py` 不打包 `platform/`），也不注册任何服务。
- HTTP 只监听 `127.0.0.1`，校验 Host；启动时把本次进程有效的登录链接写入数据目录的 `access-url`（权限 0600），`GET /login?token=` 换取会话 cookie `pa_executor_session_<端口>`（HttpOnly + SameSite=Strict，按端口隔离），无会话的页面与接口返回 401；写请求需 `x-pa-executor: 1` 与 JSON 体，体积上限 16 KiB。
- ANT（ANTHROPICUSDT）只读，且只有 Binance 可读。
- ASTER ADL 应急处理只对模拟账户运行（`src/sim-aster-trading.ts`），连接器的传输或环境不是模拟即拒绝启动；不读写旧 ASTER 模块的数据库，不涉及旧系统的普通开仓。

## 运行

需要 Node 24（使用内置 `node:sqlite` 与类型擦除），无第三方依赖；类型检查使用仓库根目录的 TypeScript。

```powershell
cd platform/executor
node src/main.ts --data-dir D:\tmp\pa-executor --port 4710   # 打开数据目录 access-url 中的登录链接
..\..\node_modules\.bin\tsc -p tsconfig.json                  # 类型检查
node --test test/*.test.ts                                     # 行为、恢复、故障注入与 HTTP 边界测试
node scripts/measure.ts                                        # 混合负载测量；未达建议预算时退出码 2
```

### 实盘金丝雀模式（3.0c）

只在用户当次授权账户、合约与金额后运行；代码已接线，尚未连过真实账户。只支持 Linux。

```bash
node src/main.ts --data-dir /home/<用户>/pa-executor-live --port 4711 --live-config /home/<用户>/pa-executor-live.json
```

配置文件（JSON，须为当前用户所有且权限 600）：

```json
{
  "notionalLimits": { "perJob": "50", "totalOpen": "100" },
  "credentialsFile": "/home/<用户>/pa-executor-keys.json",
  "accounts": [
    { "venue": "binance", "accountId": "<Binance UID>", "accountMode": "standard", "credentialVersion": 1 },
    { "venue": "bybit", "accountId": "<Bybit userID>", "accountMode": "unified", "credentialVersion": 1 }
  ]
}
```

密钥文件同样须为当前用户所有且权限 600：`{ "binance": { "apiKey": "…", "apiSecret": "…" }, "bybit": { "apiKey": "…", "apiSecret": "…" } }`。换密钥时把配置里的 `credentialVersion` 加 1 再重启（不能回退）。

启动顺序：读配置 → 按账户取本机进程锁 → 读密钥文件 → 逐个账户做启动检查（每个账户 30 秒上限）→ 建数据目录并核对环境标记 → 打开库、登记账户 → 监听。任何一步失败都拒绝启动并说明原因，启动检查失败时数据目录不被创建或改动；登记账户失败时立即交还写入租约。进程锁是 Linux 抽象套接字 `pa-executor-live/<交易所>/<账户>`，进程结束由内核释放：同一真实账户在本机只能有一个实盘执行器，换数据目录也不行（两个实例会各算各的名义金额累计，并把对方的委托当外部委托）。配置与密钥文件以非阻塞方式打开、最多读 64 KiB；密钥文件格式错误时报错不回显字段名或内容。启动检查沿用工作台执行客户端的规则：

- 两家都要求密钥绑定 IP（比工作台执行客户端更严）：Binance `ipRestrict` 须为真，Bybit `ips` 须非空且不含 `*`。
- Binance：`/sapi/v1/account/apiRestrictions` 只允许读取与所选账户模式的合约交易权限（`standard` 要“允许合约”，`portfolio-margin` 要“开启统一账户交易”），提现、划转、杠杆、期权、现货等其它 `enable*`/`permits*` 项只要不是 `false` 就要求关闭，关键项缺失也拒绝；合约账户 `canTrade` 须为真；`/api/v3/account` 的 UID 须等于配置的 `accountId`。
- Bybit：`/v5/user/query-api` 须为读写密钥，ContractTrade、Derivatives、Wallet、Spot、Options 五类权限都须列出，ContractTrade 至少含 Order、只可含 Order 与 Position，Derivatives 只可含 DerivativesTrade，其余任何类别必须为空；`/v5/account/info` 的 `unifiedMarginStatus` 须为 3–6（统一交易账户）；`userID` 须等于配置的 `accountId`。

实盘库名为 `executor-live.sqlite`（模拟仍是 `executor.sqlite`），回退到不认环境标记的旧代码时，旧代码在实盘目录里只会打开一个空的模拟库，不会拿模拟场所核对真实任务。数据目录首次使用时写入并落盘环境标记文件 `environment`（`simulated` 或 `mainnet`）；没有标记时按库文件判断（有 `executor-live.sqlite` 为实盘，有 `executor.sqlite` 为模拟）。已用于模拟的目录不能以实盘启动，实盘目录也不能以模拟启动：模拟任务与真实任务的账本、名义金额累计不能混在一个库里。连接器只把密钥交给配置里的账户与凭据版本，库里残留的其它绑定拿不到密钥（不发送任何请求）。页面标题与横幅标明实盘，确认按钮为“确认执行（实盘）”，`/api/state` 的 `transport` 为 `live`。

测量脚本在同一进程里同时跑两腿任务、4 个模拟配对的保证金划转（每配对 10 次）与 ADL 事件（每配对 10 次），三个循环按入口方式分开调度；结果为 JSON，含各循环单轮耗时、ADL 发现/首次下单/结束耗时与划转发送/结清耗时。常用参数：`--jobs`、`--pairs`、`--adl-events`、`--transfers`、`--aster-latency-ms`（给每次模拟 ASTER 调用加延迟，看慢 ASTER 是否拖住两腿任务；延迟不响应中止，须小于 ADL 下单时限 `adlOrderTimeoutMs` 3 秒，否则下单按超时处理、事件等满观察窗，运行以退出码 3 结束）、`--loop-spacing-ms`。读线程默认把历史表扫描按主键每 20000 行切成一片，每片一次读取（`--scan-chunk-rows`，0 为整表一次读取）；主线程按入口的方式每秒调用一次 WAL 维护（`--no-wal-reset` 关闭）。`--scan-chunk-rows 0 --no-wal-reset` 还原 2.5 之前的行为，用于对照。结果中的 `walReset` 为截断次数、放弃次数与耗时，`checkpointsIncomplete` 为回填线程被动 checkpoint 未能完成的次数，`readerSnapshotMaxMs` 为读线程单次读取最长占用快照的时间。数据库建在系统临时目录（可用 `TMPDIR` 指到数据盘），结束后删除，`--keep` 保留。未达建议预算时退出码 2，任务、ADL 事件或划转未全部完成时退出码 3。

### 工作台金丝雀按钮（3.0d）

系统 → 接口实测的“原油双腿金丝雀（新执行器）”一区把实盘金丝雀拆成四个按钮，每按一次起一个短进程 `server/contract-probes/oil-canary.ts`（逻辑在 `src/live/canary.ts`），沿用接口实测的规则：同一时刻只跑一项；先只读，只读给出确认短语后由操作者勾选两项确认才真实运行；真实运行只能来自同一组参数、10 分钟内最近一次只读结果，短语不符即拒绝；真实运行期间挡住系统更新；运行有总时限，超时或“停止并收尾”时不再建新任务，已在跑的任务请求停止并继续核对到终态。

- 账户：读取交易中心已保存的 Binance、Bybit 执行账户（工作台 `credentials.key` 解密，只读打开 `hub.sqlite`），账户编号取交易中心核验过的身份，凭据版本取保存修订号；账户未核验身份时拒绝。每次都先做实盘模式的启动检查（权限、IP 绑定、可交易、身份一致）并按账户取本机进程锁。
- 数据：执行器库在 `<工作台数据目录>/executor-canary/executor-live.sqlite`，目录写 `mainnet` 环境标记，只读步骤同样会打开并写这个本地库（绑定账户、记预览），但不发交易所写请求。每个进程开始时等上一进程的写入租约（被杀的进程要等租约过期，最多约 65 秒），之后与 `main.ts` 一样另起定时器每 1/3 租期续租，结束前交还。
- 上限：单笔不超过 200 USDT、累计开仓不超过 500 USDT（页面与脚本各核一次，执行器启动时固定），平仓只受单笔上限；累计从库内任务重算。
- 启动检查与核对：只读；列出两个账户该合约的持仓与挂单、金丝雀自记的自有持仓（开仓任务成交量加、平仓减，只计当前绑定账户上的腿），以及未结束或待人工确认的任务。账户持仓与自记不一致（例如旧系统或人工仓位）、有挂单、有待收尾任务，或有任务做在此前绑定的执行账户上（交易中心换过账户）时列为待处理。
- 开仓 / 平仓：有待收尾任务时拒绝。预览不下单，短语含参数、账户指纹（平仓还含自有持仓）的摘要。平仓方向取自记持仓（两边须一多一空），数量不超过两边自有持仓中较小者，不会平旧系统的仓位；两个账户的实际持仓还须与自记同方向且不少于平仓数量（防人工已平后按旧记录反向开仓）。真实运行时按当时行情重新预览再确认（价格变化后上限仍生效），然后每秒推进一次，直到任务终态或时限后 3 分钟；确认之后的任何错误都按“已发送、待核对”报告。
- 收尾：有未结束或待人工确认的任务时给出短语；真实运行把未结束任务按接管规则核对到终态（首腿撤挂单、不再新发，首腿已成交部分补发对冲腿），并把列出的待人工任务标记为已确认（页面要求操作者先在交易所处理剩余敞口）。Bybit 追价创建结果未知的任务（执行器拒绝直接确认）按“未知追价策略”一项处理：默认自动走执行器的确认未创建（创建请求已不可能送达、交易所无同时段同合约策略、持仓与挂单等于已知成交才通过，观察窗内拒绝）后再确认；不通过时可填 Bybit 策略编号认领，或强制释放（策略可能已成交）。认领与强制释放只能针对恰好一个这样的任务，做完不在同一次确认，操作者处理敞口后再收尾一次。短语含处理方式与策略编号。
- 退出码：0 任务到终态且完成；2 已发送但未确认完成（页面显示“请到交易所核对”）；1 未发送。金丝雀自己输出的账户编号只留末四位，密钥、签名与完整账户编号（启动检查失败信息会带出）按接口实测的规则隐去。
- 实盘守卫：账户写者处于隔离恢复，或交易中心有未结束的实盘执行任务时，真实运行按钮被拒。

## 真实接口契约探测（阶段 2.6a/2.6b）

`server/contract-probes/bybit-chase.ts` 与 `server/contract-probes/aster-transfer.ts`（仓库根目录下的工作台 `server/`，随发布包发布；共用代码在 `server/contract-probes/lib/`，其中 `decimal.ts` 是本目录 `src/decimal.ts` 的逐字节副本，由测试核对）是探测脚本，用真实账户核实执行器只在模拟器上成立的假设（盘点文档第 9 节第 38、39 项与 Bybit 原生追价一项）。它们不属于执行器：`src/` 仍只接受模拟传输，探测脚本不读写 `executor.sqlite`，也不经过共享写者登记。CI 只跑它们的离线测试（`test/contract.test.ts`：签名与 ethers、与工作台现有 Bybit 签名逐字节核对，写入守卫，报告脱敏，以及在替身接口上跑完整流程和故障分支），不连接任何交易所。替身（`test/contract-stub.ts`，以 `node --import` 预加载）替换 fetch，并通过 `lib/common.ts` 的等待接口让脚本的等待改走替身时钟：每次等待把时钟拨快同样时长而不占真实时间，轮询次数、截止时间与时间戳判断都与真实运行相同。这个接口只在登记的 fetch 正是当前使用的 fetch 时生效，否则脚本在发出请求前中止；脚本没有缩短等待的参数或环境变量，工作台启动探测时清空 `NODE_OPTIONS`。

运行入口有两个，守卫相同：

- 工作台页面「系统 → 接口实测」（`src/ContractProbePage.tsx`，服务端 `server/contract-probes.mjs`，盘点文档第 47 项）。页面先做只读检查，通过后显示确认内容，勾选确认才真实运行；真实运行只能来自同一接口最近一次、10 分钟内完成的只读检查，沿用其参数与脚本打印的确认短语。数据目录、凭据文件与报告路径由服务端固定，请求只能在白名单内选标的、账户前缀与数值。同一时刻只运行一项；真实运行期间占用执行入口，系统更新被挡住。Windows 上的工作台只能做只读检查（停止信号在 Windows 上会直接结束进程，脚本无法收尾）。报告与运行过程保存在数据目录 `contract-probes/`（保留最近 10 次），可在页面下载。Bybit 用交易中心保存的执行账户，ASTER 用模块 `.env` 中 `_USER`、`_SIGNER`、`_PRIVATE_KEY` 三项齐全的前缀。
- 命令行（下文命令，在仓库根目录运行）。

运行前的准备（脚本无法替操作者检查的部分）：

- 运行期间旧系统不得在同一标的（Bybit）或同一对子账户（ASTER）上下单、追价或划转。ASTER 的 A、B 有持仓时，先暂停该配对的保证金平衡，再加 `--balancer-paused`；否则脚本拒绝发送。
- ASTER 的请求权重按 IP 计。脚本每次流水读取权重 30，生产 ASTER 模块与它共用出口 IP 时可能一起触发限流：在生产主机上运行时先暂停生产 ASTER 模块的轮询，或换一个出口 IP 运行。脚本看到已用权重达到 1200 时暂停读取 5 秒，报告的 `requestWeight` 记录峰值。
- `--probe-nonce` 用主账户 API signer 发送带偏移的 nonce。交易所若要求同一 signer 的 nonce 递增，一笔被接受的未来 nonce 会让生产划转在这段时间内被拒；探测期间生产划转应保持暂停，正偏移不要超过能接受的暂停时长。

共同规则：

- 默认只读。发送真实委托或划转必须同时带 `--live` 与 `--confirm <短语>`；短语由只读运行打印，Bybit 的短语包含标的、数量与被动价距离，ASTER 的短语包含金额、A/B 凭据前缀与各个 nonce 偏移，参数变了短语随之改变。
- 硬上限写在脚本里：ASTER 的 `--amount` 不超过 5 USD1，nonce 探测最多 8 笔（每笔在 `--amount` 上依次多 0.01，单笔最多 5.08，逐笔划回；探测期间 B 上累计最多约 40.4 USD1）；Bybit 只用最小下单量，同时最多两笔挂着，两笔的名义金额超过 `--max-notional`（默认 50 USDT，最高 200）即中止，标的限 CLUSDT、BZUSDT、SKHYUSDT、SKHYNIXUSDT。
- 结果未知的写请求不重发：脚本停止后续写入，以退出码 2 结束（ASTER 划转超时或返回不确定的应答时先按余额与流水观察；被网关拦截时直接停止，不再读取）。只有旧客户端拒绝码清单内的错误码算明确拒绝，其余错误码、超时、5xx 与网关拦截都按结果未知处理。唯一的例外是 Bybit 收尾会对仍未结束的自有策略再发一次停止。
- 每次请求固定超时（ASTER 读 8 秒、划转 15 秒；Bybit 12 秒），不自动重试，不跟随重定向；遇到 HTTP 403、418、429 或 ASTER 限流错误码（-1003、-1015）立即停止。
- 报告文件在发出第一个请求前创建（当前目录的 `contract-*.json`，`--out` 可改；文件已存在即中止），已隐去密钥、签名、账户编号与长十六进制串，钱包地址只保留首尾；余额、数量、价格、策略编号与订单号保留。
- 第一次 Ctrl-C 停止后续步骤：Bybit 照常收尾（仍会访问交易所），ASTER 只写报告、不自动划回。第二次立即退出，报告文件留空。
- 退出码：0 正常结束；1 未发出任何写请求即中止（含发送前被中断）；2 已发送过写请求但未正常收尾、有写请求结果未知，或收尾后未能确认无残留，须在交易所核对。

Bybit 原生追价（2.6a）：

```bash
node server/contract-probes/bybit-chase.ts --symbol CLUSDT --data-dir <工作台数据目录>        # 只读，打印确认短语
node server/contract-probes/bybit-chase.ts --symbol CLUSDT --data-dir <工作台数据目录> --live --confirm <短语>
node server/contract-probes/bybit-chase.ts --symbol CLUSDT --data-dir <工作台数据目录> --allow-fill --live --confirm <短语>
```

凭据从工作台数据目录的 `hub.sqlite` 与 `credentials.key` 只读解密（执行账户里的 Bybit 一行），或用环境变量 `BYBIT_API_KEY`、`BYBIT_API_SECRET`（可放在 `--env-file`，与 `--data-dir` 二选一；进程环境变量优先于文件中的同名项）。`--data-dir` 不会在数据目录里新建文件：数据库没有未合并的 WAL 时按不可变方式打开，有 WAL 时要求工作台正在运行，否则中止并提示改用环境变量。

`--live` 先要求该标的没有持仓、挂单和运行中的追价策略，然后创建买入追价（最高追价低于买一 `--passive-bps`，默认 200 个基点，不预期成交）、查询、重复创建、停止、重复停止，并各发一笔数量低于最小量和时间戳过期的创建以记录拒绝码。`--allow-fill` 另发一笔最高追价高于卖一的追价（预期成交）。任何一次停止之后 `--settle-timeout-s`（默认 60 秒）内未确认策略已结束且子单结清，脚本不再创建新策略，直接进入收尾。

收尾只处理能确认属于本次运行的东西：停止回执带回编号的策略；某笔创建结果未知（应答丢失、被网关拦截或返回清单外错误码）时，另外接管在该请求可能到达的时间窗内创建、买入开仓且数量相同的运行中策略，扫描持续到该请求最晚可能到达之后 10 秒，这种运行即使收尾干净也以退出码 2 结束（同一时间窗内他人创建的同方向同数量策略无法区分，所以运行期间该标的不得有其他追价）；然后用只减仓市价单平掉这些策略回报的已成交数量（不超过当时持仓），被动追价意外成交时同样平掉。收尾的任何一次列表读取失败或分页不完整都不算“无残留”，以退出码 2 结束。

ASTER 子账户划转（2.6b）：

```bash
node server/contract-probes/aster-transfer.ts --env-file <ASTER 模块的 .env> --master-prefix <主账户前缀> --a-prefix <子账户 A 前缀> --b-prefix <子账户 B 前缀>
node server/contract-probes/aster-transfer.ts <同上> --amount 1 --live --confirm <短语>
node server/contract-probes/aster-transfer.ts <同上> --amount 1 --probe-nonce=-30,-59,-61,-90,-121,61 --live --confirm <短语>
```

凭据按旧模块的约定读取 `<前缀>_USER`、`<前缀>_SIGNER`、`<前缀>_PRIVATE_KEY`（进程环境变量优先于 `--env-file` 中的同名项）。只读运行读取子账户列表、两侧余额、持仓数与最近流水（`--history-minutes`，默认 30；流水返回满 1000 行即视为不完整并中止）。`--live` 从 A 向 B 划 `--amount`（默认 1 USD1）再划回，每笔之后轮询两侧余额与流水直到全部可见或超过 `--settle-timeout-s`（默认 300 秒），并用新流水测 `endTime` 的开闭。

`--probe-nonce`（必须写成 `--probe-nonce=…`）按给定的秒数偏移各发一笔 A→B 划转以探测 nonce 有效期，被接受的每一笔都是真实划转。偏移按从小到大发送，每笔金额不同、发送后单独按余额与流水核对；每笔发送前先等到它的 nonce 晚于主账户 signer 此前用过的所有 nonce（偏移 -N 秒至少等 N 秒），所以拒绝不会是 nonce 递增要求造成的。交易所返回清单外错误码（旧模块视为结果不确定的 -1000、-1001、-1006、-1007 除外）时，观察到该 nonce 按假设应已过期之后（75 秒加正偏移；`--settle-timeout-s` 小于这个时长时脚本在发送前中止，默认 300 秒下正偏移最大 225 秒，调到 900 秒时最大 825 秒），期间每次读取都成功且两侧无变化的记为 `refused-unlisted` 并继续；超时、5xx、不确定的错误码、观察期间有读取失败，或已回执却未在限时内可见，则停止探测，不自动划回。探测结束后把已入账的各笔按原金额逐笔划回，最后按流水净额核对，净额不为零以退出码 2 结束。EIP-712 签名为脚本自带的无依赖实现（`server/contract-probes/lib/eip712.ts`），不是恒定时间实现，只用于操作者在自己主机上的一次性探测。
## 关键语义

- 未知结果不重发：发送中断记为 `unknown`，按原客户订单号核对；过观察窗、间隔多次查无且账户无痕迹才判定 `not-created`。
- 单写者租约带代次：租约过期后实例永久停止写入；新实例接管时把 `prepared` 记为 `not-sent`、`sending` 记为 `unknown`。接管后首腿不再新发并撤挂单；首腿已成交部分按落盘进度补发对冲腿（目标量减已对冲量，取整到步长，用新的客户订单号 `…-1r<n>`），仍经过账户绑定、数量与持仓守卫，价格偏离不阻断补发。正常关闭交还租约。
- 对冲腿 IOC 部分成交也按差额补发，每任务最多 `hedgeAttempts`（5）笔；最后一笔被交易所明确拒绝或已请求停止时不补发。
- 价格保护：预览按 `maxSlippageBps`（默认 50，可在意图中设 1–1000）算出首腿界限；发送前两腿盘口须新鲜、接收时间相差不超过 `pairQuoteWindowMs`，越过界限不发送；市价首腿以界限价 IOC 限价发送，由交易所执行保护。
- 保留期：已结束、委托全部结清且无待确认人工项的任务，其事件、命令与已消费预览超过 90 天后分批删除；任务与委托记录保留。WAL 见下一项。
- WAL 维护（阶段 2.5，`src/store.ts` 的 `maintainWal`）：只要始终有读取方在读，自动 checkpoint 就不能让 WAL 从头复用，`journal_size_limit`（64 MiB）也不起作用。入口每秒检查一次，WAL 超过 16 MiB 时做一次截断式 checkpoint；它在等待期间占着写锁，所以每次锁等待最多 250 ms，之后恢复 `busy_timeout`。读取方未让出时放弃，按 1 秒起、逐次加倍、最长 60 秒重试；WAL 超过 64 MiB 时入口向标准错误输出一次告警。前提是所有读这个库的连接都只用短语句：有连接长时间占着同一快照时截断无法完成，WAL 继续增长，每次重试期间写锁被占（开发机实测每次约 0.37–0.39 秒，由若干次最多 250 ms 的锁等待组成，上界未核实；盘点文档第 8.3 节）。失去写入租约或正在关闭的实例不再做 WAL 维护。
- 共享写者登记（注入时）：每个账户单独认领；建单与撤单先登记再发送，出站前复核所有权，本地结果落盘后再结清登记；同一账户有未核对的登记操作时不发送新委托；重启后按本地事实结清遗留登记（未发送的记为未执行，核对到委托的记为已确认，撤单在签名有效窗口过后仍见挂单才记为未执行）。所有权丢失、租约过期或登记库被替换时执行器整体停止写入。只运行不交易时不认领账户。
- `attention`（敞口不平衡、对冲腿被拒、对冲补发用尽、撤单用尽或被登记阻止超时、委托过观察窗仍未知、对冲腿账户读取或登记持续失败）保留合约锁并继续核对，人工确认后才释放。
- 预览要求两腿桶数完全相等；对冲量按首腿实际成交换算并向下取整到对冲所步长。
- 名义金额硬上限（3.0a，`createExecutor({ notionalLimits: { perJob, totalOpen } })`，USDT）：启动时固定，页面与接口不能修改；`mainnet` 环境有下单连接器而未配置时拒绝启动，模拟默认不设。任务名义金额取两腿中较高的一腿，按“价格保护界限、卖一价、限价”中最高者乘桶数计；预览与确认事务内各核一次，超限返回 `notional_job_cap` / `notional_total_cap`，不建任务、不下单。累计只计开仓任务：从确认起计入，成交、撤单、平仓都不退回；只有没有任何委托离开进程就结束的任务（委托全为 `not-sent` 或没有委托，如接管时尚未发送）不计。平仓只受单笔上限。累计每次从库内任务重算，重启与改上限后仍有效。对冲腿市价补发不设价格上限，真实成交金额可能高于估算。配置上限时拒绝卖出方向的追价首腿（`notional_chase_sell`）：它只有最低价，可在整个任务时限内向上追。
- 真实连接器（3.0b，`src/live/binance.ts`、`src/live/bybit.ts`，`transport: 'live'`）：由实盘金丝雀模式（3.0c）接入，目前只由替身测试覆盖（含在替身交易所上驱动执行器跑完两腿开仓与 Bybit 追价平仓的端到端用例），未连过真实账户。端点、拒绝码清单与时间戳码沿用生产客户端 `server/trading-execution-exchanges.mjs`（未修改它），签名与有上限的 JSON 读取复用 `server/exchange-transport`。分类：发送前守卫（`beforeSend`）拒绝、凭据缺失、本地参数无效与持仓模式读不到才报 `not-sent`；`fetch` 调用之后的任何失败（超时、中止、重定向、应答过大或无法解析）对写入一律 `uncertain`、对读取一律 `read-failed`；只有清单内的拒绝码报 `rejected`，其余码与 5xx 为 `uncertain`。时间戳被拒（Binance -1021、Bybit 10002）证明未执行：同步一次服务器时钟（偏差上限 300 秒）后用同一参数重发一次，重发前守卫再跑一次；再被拒、同步失败或守卫拒绝重发都报 `rejected`。账户快照每个合约先读委托（Bybit 还读状态 2/4/5/6 的追价策略，记为外部委托 `chase-<编号>`）、后读持仓，读的间隙成交的委托会体现在后读的持仓里；账户编号取 Binance `uid` / Bybit `userID` 的全部位数，60 秒内复用。下单前按 60 秒内的持仓模式缓存（换密钥即失效，过期则现读）：双向持仓时只减仓标记必须与仓位方向一致，否则不发送；Bybit 单向持仓还要求仓位方向能由买卖方向与只减仓标记推出。回报逐项核对客户订单号、合约、方向、类型、限价与有效方式、仓位方向、只减仓与数量，不符时写入应答报 `uncertain`、查询报 `read-failed`。Bybit 下单与撤单只回执编号：下单后读一次委托，读不到就按已受理、未成交报告；撤单后读不到则报 `uncertain`。查单先查 `/v5/order/realtime` 再查 `/v5/order/history`。Bybit 追价按盘点第 47 项的真实形状：`chasePercentE4: 0`，策略记录没有 `positionIdx`（仓位方向由买卖方向与只减仓推出），子单 `orderType` 接受文本 `UNKNOWN`，只有状态 3（已结束；状态 4 仍在结束中）、无挂着的子单、子单成交合计等于策略成交量，且 `/v5/order/realtime` 里该合约同方向没有未结束的追价挂单（`createType: CreateByChaseOrder` 或不带客户订单号）才算结清——挂单期间子单列表为空，挂单只在 realtime 里；策略编号不是本进程创建的就逐个执行合约查找（查无编号返回空列表）。`listStrategies` 读状态 2/4/5/6 全部（4 只保留时间窗内创建的）与状态 3 的时间窗，后者同生产客户端按 7 天减 2 秒分段（每段起点提前 1 秒、终点向上取整），总时间窗超过 366 天报读取失败；账户快照对外部策略只取编号与合约。Bybit 下单后的跟进读取只在读取失败或查无时退回按回执报告，查到但不符或编号不同报 `uncertain`。凭据格式同生产客户端（密钥为可见 ASCII、密文不含换行），不符时不发送。分页游标重复、满页无游标、超过 40 页均报读取失败。
- 调度：入口 `main.ts` 把两腿任务（`tickJobs`）、保证金划转（`tickTransfers`）与 ADL 应急处理（`tickAdl`）作为三个循环分别调度，每轮结束后间隔 1 秒（连续失败时逐次加长），持仓展示另有自己的循环；一个循环里的交易所调用变慢只拖住它自己。每个循环同一时刻只有一轮，重复调用并入在途轮次。三个循环共用写入租约、事件表与命令表（只新增行），在途时不改写彼此的记录：ADL 只读取配对记录，两腿任务循环里的保留期清理只删除超过保留期且已结清或已结束的划转与 ADL 记录。旧系统同一配对的保证金平衡与 ADL 在一把配对锁内串行（盘点文档 6.5），这里按发送互斥保留这一点：配对有划转处于 `prepared` 或 `sending` 时，ADL 不发新批次，事件记为受阻（“配对的保证金划转正在发送……”），每秒重看一次，受阻时间不计入 1800 秒处理时限；配对有 ADL 减仓单处于 `prepared`、`sending` 或 `open` 时，划转本轮不发（“ADL 减仓单正在发送或挂单，本轮不划转”），按检查间隔再看。ADL 在读取现场前、划转在读取余额前各查一次，落盘事务内再各查一次；等待通常以划转发送时限（`callTimeoutMs`）和减仓单的撤单周期（最多 3 次、每次间隔 `adlCancelAfterMs`，再加一次查询）为上界，但撤单次数用尽后仍挂着的减仓单会一直阻挡划转，直到慢速核对（`adlActiveQueryMs`，30 秒）确认它已在交易所结束或被人工撤掉；结果未知的划转或减仓单不互相阻挡。`tick()` 依次跑三个循环各一轮，供测试使用。
- 入口任一执行循环连续失败 5 次或失去租约时交还租约并以非零码退出，由外部重启接管；关闭时打断各循环的等待间隔，只等在途轮次结束。
- 数量与价格用精确十进制字符串，不经过浮点。
- Bybit 原生追价（首腿 `orderType: 'chase'`，只限 Bybit 首腿；对冲腿仍为市价 IOC）：交易所不接受客户编号，本地客户订单号只用于本地记录与共享写者登记；追价腿不带 `limitPrice`，`maxChasePrice` 取预览的价格保护界限 `priceBound`。ACK 回报的策略编号先落盘（仅供人工查看），再按该编号查询一次，合约、方向、仓位方向、数量、最高追价与只减仓全部一致、且创建时间在准备时刻减 `adoptSkewMs` 至收到 ACK 时刻加 `adoptSkewMs` 之内才采用该编号（ACK 时查询失败、之后才查到的，首次核对同样检查创建时间）；编号已被其他委托认领、查无、身份不符或创建时间不符按创建结果未知处理。查询读取失败时保留编号但在查询核对身份前不对其发送停止；之后查无、身份不符、创建时间不符或超过宽限仍未核对，同样按创建结果未知处理（编号记入备注；该建单的共享登记已在保留编号时按已确认结清，不再撤回，同账户其他合约不受其阻止，同合约仍由合约锁挡住）。已核对的编号之后查到身份不符则转 `attention`，且不再停止该编号。按策略编号核对状态、成交量与均价，成交量回退、已结束后又回报未结束、超量的回报拒收。截止、停止请求或策略暂停时停止策略并必重查；终态后子单未结清超过宽限即转 `attention`。创建结果未知时不重发：ACK 丢失或接管时发送中的策略记为未知且无策略编号，任务转 `attention`，人工可填写策略编号认领（创建时间须在准备时刻减 `adoptSkewMs` 至发送时刻加调用超时与 `adoptSkewMs` 之内、身份一致、未被其他委托认领、请求编号幂等）、在建单观察窗后确认未创建（列出账户同合约策略，有运行中、暂停的未认领策略，或发送时刻前后 `venueClockToleranceMs` 内创建的未认领策略即拒绝，持仓与挂单须与已知成交一致），或强制释放；未处理前不能确认人工处理。认领的策略在认领时立即停止一次，之后待人工期间仍有界停止（停止合计最多发出 `cancelAttempts` 次；未发送的不计），人工确认处理后不再停止。共享写者登记的建单载荷含 `strategy: 'chase'` 与 `maxChasePrice`，停止策略按策略编号登记。
- ASTER 保证金平衡划转（阶段 2 第三批，`src/transfer.ts`，模拟连接器 `src/sim-aster.ts`）：一个配对是同一主账户下的多侧与空侧子账户（`0x` 小写地址），不占用 `accounts` 表，由 `registerTransferPair` 登记（新配对默认停用，更换任一账户会停用并改变身份指纹；同一主账户下两个子账户与已有配对完全相同的配对，不论多空方向都以 `pair_duplicate` 拒绝），`POST /api/transfer-pairs/:id/enable|disable`（带 `requestId`）启停，启用前先读子账户列表核对归属。每轮对已启用、无未结清划转、过冷却与检查间隔的配对读两侧余额并规划：差额 = 多侧可用 − 空侧可用，绝对值须严格大于 `threshold`，金额 = min(差额一半, `maxTransfer`, 转出侧可划上限, 转出侧可用 − max(权益, 0) × `bufferRatio`)，向下取整到 1e-8，低于 `minTransfer` 不划。可用余额可以为负（按无可划处理）。余额快照须在 `transferBalanceMaxAgeMs`（8 秒）内取得，且晚于本配对及共用账户的配对上一笔划转的结算时刻，否则本轮不划；接收时刻（`receivedAt`）超前本机时钟超过 `futureToleranceMs`（1 秒，与盘口共用）的快照同样拒绝，说明里写明超前量，回执后的余额刷新也不接受这样的快照。有计划时在动作内依次：重读子账户列表（两侧须在所配主账户名下且未冻结）；尽力读取两侧近 `transferClockToleranceMs`（60 秒）内的流水作为发送前基线（每侧超时 `transferBaselineTimeoutMs` 1.5 秒，读不全或同额超过 100 条的一侧不记，不阻塞发送）；最后重读两侧余额、再校验时效并重新规划，金额以这次为准。然后在落盘事务内再次校验互斥、冷却、余额时效与配置未在评估途中被改（被改则本轮不划，下一轮按新配置规划），落盘 `prepared`、标记 `sending`、出站前复核写者租约、发送。
  - 状态：`prepared` → `sending` →（`acknowledged` → `confirmed`）/ `rejected` / `not-sent` / `unknown`；`unknown` → `confirmed`（`late_receipt_confirmed`）/ `expired-not-executed`（`nonce_expired_no_receipt`）/ `expired-unverified`（`nonce_expired_partial_receipt`、`nonce_expired_ambiguous_receipt`、`nonce_expired_unreadable`、`identity_changed`）。依据记在 `label.basis`。
  - 已回执（`acknowledged`）不再发送任何请求，只等两侧余额快照都晚于回执时刻后记为 `confirmed`；刷新失败每 `transferRetryMs`（5 秒）只读重试，最多到回执时刻（已落盘）之后 `transferRefreshDeferMs`（300 秒）：到期仍读不到则按回执记为 `confirmed`，标签注明“余额未刷新”，`balancesRefreshedAt` 为空，同一事务登记已用流水与冷却（已用流水同时记到所有共用账户的配对上）。这样一个再也读不到的账户不会永久挡住该配对或接管后的所有配对；之后的规划仍须读到新的余额才会发送。
  - 划转接口没有客户端编号：结果未知（超时、网络错误、回执无法解析、成功码但未确认成功）的划转永不重发、也无法按身份查询。到期时刻 = 发送时刻 + max(`callTimeoutMs` + 连接器 `requestValidityMs`, `transferHistorySpanMs`)（模拟为 180 秒），在标记发送时算出并写入划转记录（`readyAt`），结算按落盘值，之后调小预算重启不会提前结算；没有该字段的旧记录按当前预算现算。到期后读一次两侧流水打标签并结算，全自动、没有人工环节。候选流水 = USD1、划转类型、金额相等、方向正确、时间在 [发送 − 60 秒, 到期] 内，排除发送前基线与已归属给之前划转的流水（已用流水按时间保留 2 × `transferClockToleranceMs` + `transferHistorySpanMs`，即 300 秒，超过的在下一次落盘划转时清除，不按条数截断）；回执带回交易编号提示时只认该编号。只有同一次两侧完整读取中各恰好一笔且交易编号相同（无编号提示时还须不早于落盘时刻所在整秒减 `futureToleranceMs`：真实流水时刻截断到整秒，实测可比发送时刻早 396 毫秒）才记为已执行；两侧都有但不是一对一同编号记为归属歧义；只有一侧、或读取不完整记为部分匹配；完整读取两侧都没有记为未执行。读取失败或不完整时推迟，最多 `transferLabelDeferMs`（300 秒），之后按已累积的证据（最多 20 条）结算，没有证据即不可读。标签、终态、已用流水与配对冷却在同一事务提交。
  - 冷却：回执或明确拒绝后从发送时刻起 `cooldownMs`（同旧实现发送前写入的 `created + cooldown_seconds`）；未知结算后从结算时刻起 max(`cooldownMs`, `transferSettleCooldownMs` 30 秒)，部分匹配、归属歧义、不可读与无交易编号的确认为 max(`cooldownMs`, `transferUncertainCooldownMs` 300 秒)。已用流水与冷却按配对保存，所以结算时把归属的流水同步登记到所有共用账户的配对；上述是否到账不确定的结算还让这些配对从结算时刻起同样等 `transferUncertainCooldownMs`。旧实现只对部分匹配、归属歧义与无编号确认用 300 秒，不可读为 30 秒；这里不可读也取 300 秒，是有意的保守偏离。未发送不进冷却，按检查间隔指数退避：连续第 n 次未发送等 `checkIntervalMs` × 2^(n−1)，上限 max(`cooldownMs`, `checkIntervalMs`)，连续次数记在配对上（重启后延续），有一次发出即清零。冷却或退避后按新读到的余额重新规划，用新的请求编号；同一笔请求从不重发。
  - 互斥与恢复：同一配对或共用任一子账户的配对有未结清划转时不发新划转。接管时 `prepared` 记为 `not-sent`、`sending` 记为 `unknown`（不重发，按到期结算），`acknowledged` 继续刷新余额；接管时未结清的划转结清之前，所有配对都不发新划转。同实例内中断在 `prepared` 或 `sending` 的划转下一轮按同样规则处理。
  - 共享写者登记（注入 `control` 时，阶段 2.6c）：每笔划转在本地落盘 `prepared` 之后、标记 `sending` 之前登记为 `platform:transfer:<划转编号>`，认领主账户与两个子账户（`aster` 身份，与执行器同一环境），载荷是登记库校验的保证金划转意图（`/fapi/v3/subAccountTransfer`，`USD1`，`FUTURE_FUTURE`，只作记录，不发送）；出站前在 `beforeSend` 内复核登记所有权，本地结果落盘后结清登记（已回执记为已执行，被拒或未发送记为未执行，未知保持未知）。登记拒绝时该笔记为未发送并按未发送退避，传输未调用。每轮划转处理的开头与末尾按本地事实结清遗留登记：`prepared`、`not-sent`、`rejected`、`expired-not-executed` 记为未执行，`acknowledged`、`confirmed`、`expired-unverified` 记为已执行（可能已执行也按已执行），仍在发送或未知的不动，正在发送的一笔与没有本地记录的登记不碰。登记库对本模块的未知划转按 ASTER 签名有效期过期规则处理：最后更新 120 秒后不再挡同组账户的写入，新划转也不再被本模块过期的未知写入挡住；不跨模块。因此注入登记时划转连接器的 `requestValidityMs` 不得超过 120 秒（`REGISTRY_ASTER_EXPIRY_MS`，与登记库 `ASTER_WRITE_EXPIRY_MS` 由测试核对相等），否则拒绝启动。入口 `main.ts` 不注入登记，自动登记一个默认停用的模拟配对。
  - 预算与隔离：划转的每次读取（余额、子账户列表、标签流水）超时 `transferReadTimeoutMs`（8 秒），发送仍用 `callTimeoutMs`（到期公式依赖它）。每轮划转处理合计超过 `transferTickBudgetMs`（10 秒）后不再开始下一笔，剩下的下一轮优先处理；已开始的一笔会做完，所以一轮最长约为预算加一笔的耗时。单笔划转或单个配对出错只影响它自己（损坏的未结清记录只挡住所属配对与共用账户的配对）。未结清划转的结算抛出租约失效以外的异常时记 `transfer-settle-failed` 事件（含配对、划转编号、原因与连续次数；同一划转同一原因每 5 分钟最多一条，限频状态只在内存，重启后重新记一条），所属配对与共用账户配对的 `blocked`（页面“说明”列）改为“未结清划转记录损坏，需人工处置”或“未结清划转结算出错（连续 N 次：原因），持续出错需人工处置”，与正常等待到期的“有未结清的划转”区分开；处置步骤见“人工处置”。配对记录本身损坏时该行不列出、不评估，编号计入 `/api/state` 的 `transfers.corruptPairs` 并在页面提示，状态接口与其余配对不受影响。整个划转处理出错只记 `transfer-tick-failed` 事件（同一错误文本每分钟最多一条，限频状态同样只在内存），不影响两腿任务与登记结清；只有失去写者租约会向上传播。启动时校验划转预算均为正整数、连接器 `requestValidityMs` 为正整数、`transferClockToleranceMs` 小于 `transferHistorySpanMs`，不满足即拒绝启动；值为 `undefined` 的预算覆盖项按默认值处理。
  - 耗时：按默认预算，单个配对一轮评估在每次调用都拖到超时前才返回时最坏串行耗时 68.5 秒：规划用余额 8 秒（两侧并行）+ 子账户列表 8 秒 + 发送前基线 1.5 秒（两侧并行）+ 重读余额 8 秒 + 发送 35 秒（`callTimeoutMs`）+ 回执后刷新余额 8 秒（两侧并行）。时间预算只在两笔之间检查，所以一轮划转处理最长约 10 + 68.5 = 78.5 秒，这段时间只有划转循环被占用，两腿任务与 ADL 照常推进（见“调度”）。
  - 保留期：已结清的划转记录与启停命令超过 `historyRetentionMs` 后随 `prune()` 删除，未结清的不删；已用流水、冷却与退避记在配对上，不随记录删除。

- ASTER ADL 应急处理（阶段 2 第四批，`src/adl.ts`，模拟连接器 `src/sim-aster-trading.ts`，切片决定见盘点文档第 9 节第 40/41 项）：对每个已登记的划转配对运行，与该配对的划转是否启用无关。
  - 发现：连接器推送的 ADL 成交与按窗口扫描的成交历史（每 `adlScanIntervalMs` 60 秒一轮，回看重叠 `adlScanOverlapMs` 60 秒，每轮最多 `adlScanRequests` 2 次请求；整页即按中点二分窗口重读；读取失败或相邻毫秒内仍满页的窗口保留待查并移到队尾轮转，之后的时间照常入队扫描，待查窗口最多 100 段，超过即把最新一段延长；页面显示待查段数与说明）合并为证据，按交易编号去重；同一编号前后不一致记为冲突，成交量只增不减。子账户首次被本配对看到之前创建的 ADL 订单（推送与历史一致）不追溯。无效推送丢弃并记 `adl-push-dropped`，内存推送队列上限 1000 条，溢出丢最旧并计数；推送落盘失败时放回队列，连续 3 次失败即丢弃这批并计数。
  - 事件：有未处理的 ADL 证据即开事件（只有净差、没有 ADL 证据不开事件；每个配对同时最多一个未结束事件）。每轮先读两侧持仓（8 秒内的快照才算有效），要求持仓已反映所有已知 ADL 成交与近 24 小时内有成交的减仓单（L054：持仓的交易所更新时间不早于首次看到当前累计成交的回报时间；之后只改状态、不增成交的回报不推进这个时间。首次看到成交的回报晚于成交本身时，例如挂单部分成交后被撤，持仓更新时间晚于最近一次已知成交更少的回报时间（ADL 订单取创建时间），且距首次看到该成交已过 `adlObservationMs` 120 秒，也视为已反映；减仓批次的第一份回报就带成交时，以规划所用持仓的更新时间作为“成交更少”的时刻），有挂单、证据冲突、子账户与其他配对共用、读取规则失败时受阻不下单，受阻时间不计入运行时限。
  - 减仓：按合约算出多侧多空差额，只对多出的一侧下只减仓市价单，不设价格上限；单批名义金额上限 `batchNotional`（默认 1000 USDT，按标记价向下取整到步长）。差额小于最小下单量记为残差、按完成处理，事件记录残差数量与方向；上限买不到一手时该合约保持受阻。页面可关闭自动减仓（只核对，两侧被手工平衡后事件自动完成）或修改上限，请求编号幂等。无交易权限时受阻。
  - 委托：落盘 `prepared` → `sending` → 发送（`adlOrderTimeoutMs` 3 秒），落盘前复核事件版本与写者租约。明确拒绝、未发送、成交、挂单按回报处理；结果未知的不重发，按原客户订单号查询最多 `adlQueryLimit` 3 次（间隔 2 秒），观察 `adlObservationMs` 120 秒仍无回执即按新现场继续（迟到回执撤销该判定），之后每 30 秒仍查一次。挂单超过 `adlCancelAfterMs` 10 秒先落盘撤单意图再撤单；撤单结果未知或被拒、之后查到仍在挂单的，每 10 秒再撤，同一批最多 3 次；最后一次撤单 10 秒后查询仍在挂单，即停止配对当前未结束的事件的自动减仓（`halted`，观察中的事件继续观察），说明写明需人工在交易所撤单，挂单结束后再重新开始。回报倒退（成交量减少、终态回到未终态）拒收并受阻。
  - 停止：最后一批被拒绝、连续 3 批零成交、连续 `adlNotSentLimit` 20 次未能发出（L084）、运行时间（只计 `active`）超过 `adlMaxActiveMs` 30 分钟或批次超过 `adlMaxBatches` 500 时停止自动减仓（`halted`），继续核对，两侧平衡后照常完成。页面“重新开始自动减仓”（`POST /api/adl/incidents/:id/restart`，带 `requestId`，只接受已停止的事件）重置时限与批次计数，所有守卫照常。
  - 结束：两侧总量一致（含残差）即完成；有结果未知的减仓单时继续观察到该单最晚可能发送时刻之后 `adlWatchMs` 10 分钟，期间每 10 秒读一次现场，再现净差即结束本事件并开新事件（`parentId` 指向原事件），观察期满后未知的委托按未知结清；观察期内迟到回执使批次重新挂单的，等它结清后才结束观察。没有未结束事件时，配对上残留的未结清批次照常核对与撤单。
  - 恢复：接管时 `prepared` 记为未发送、`sending` 记为未知（不重发，按上面的查询规则核对）；同实例内中断同样处理。
  - 共享写者登记（注入 `control` 时，阶段 2.6c）：每批减仓单在批次落盘后、标记 `sending` 之前登记为 `platform:adl:<客户订单号>`，只认领该批的子账户；撤单在计数加一之前登记为 `platform:adl-cancel:<客户订单号>:<尝试戳>`（每次尝试一个新编号：本进程内严格递增、且大于该批上次撤单时刻的毫秒戳，落盘为本次的撤单时刻），载荷带撤单意图与目标。两者都在 `beforeSend` 内复核登记所有权（预算 `adlOrderTimeoutMs`），本地结果落盘后结清：减仓单有回报记为已执行，被拒或未发送记为未执行，未知保持未知；撤单只有确定未发送记为未执行，其余记为已执行（撤单不会增加敞口，订单结果由批次核对决定）。登记拒绝时减仓批次记为未发送：可自行消除的拒绝（同账户有未结清的登记操作、登记库忙、上一持有者仍在运行）等 `adlRetryMs` 后重试，不计入连续未发送停止；其余拒绝照常计入。撤单被登记拒绝时不计撤单次数，`adlRetryMs` 内不再撤、照常按原客户订单号查询（人工在交易所撤单后批次即结清）：可自行消除的拒绝到期再撤，其余拒绝（例如账户被其他模块固定）即停止配对当前未结束的事件交人工（观察中的事件追加说明），与撤单用尽同样处理。每轮 ADL 处理的开头与末尾按本地事实结清遗留登记：减仓单 `prepared`、`not-sent`、`rejected` 记为未执行，`open`、`done`、`unknown-verified`、`unknown-closed` 记为已执行，发送中与未知的不动；撤单按批次的撤单时刻判断是否发出过（撤单时刻早于该尝试戳即从未标记或已退回，记为未执行，否则记为已执行）。注入登记前留下的挂单批次接管后照常撤单（撤单登记，原单不补登记）。入口 `main.ts` 不注入登记，模拟配对在 BTCUSDT 上有多空各 0.05 的持仓，可用模拟连接器的 `adl()` 场景触发。
  - 预算与隔离：每轮 ADL 处理合计超过 `adlTickBudgetMs` 10 秒后不再开始下一个配对，下一轮从中断处继续；单个配对出错记事件，不影响其他配对；ADL 有自己的循环，不等两腿任务与划转。配对换账户时有未结束事件、未处理证据或未结清减仓批次以 `adl_incident_open` 拒绝。页面与 `/api/state` 的账户编号只显示末 4 位。
  - 保留期：已结束事件、其已结清批次与已处理证据超过 `historyRetentionMs` 后随 `prune()` 删除；配置与扫描进度留在 `adl_pairs`。
- ASTER 账户持仓只读展示（阶段 2.3c，`src/positions.ts`，模拟连接器同为 `src/sim-aster-trading.ts` 的 `positions()`）：读取每个已登记划转配对多侧与空侧子账户的全部持仓，只展示，不写库、不下单，与划转是否启用无关。
  - 调度：入口 `main.ts` 在两腿任务循环之外单独调度 `executor.refreshPositions()`，按本轮耗时补足 `positionsRefreshMs`（15 秒）间隔；同一时刻只有一轮，重复调用并入在途轮次；同一子账户被多个配对引用时每轮只读一次；最多 `positionsConcurrency`（4）个账户同时读取，单次读取时限 `positionsReadTimeoutMs`（8 秒）。`/api/state` 只读内存结果，不等待交易所。
  - 时效：采样时刻取读取开始的本机时间。最新读取成功为“最新”；失败时继续显示上次结果并注明原因（“最近一次读取失败”），上次成功采样超过 `positionsMaxAgeMs`（45 秒，须大于间隔与时限之和）后不再显示任何行；本机时钟回退同样视为不可用。页面自身刷新失败时提示持仓停留在哪一时刻。
  - 汇总：两侧都在有效期内时按合约列出多侧账户净持仓、空侧账户净持仓与两侧合计；只有两侧最新读取都成功时才判断多空总量一致或不一致，合计算法与 ADL 处理的平衡判定相同（两侧带符号合计为零），但 ADL 处理同时读取两侧，展示这边两侧各自采样：两侧采样相隔超过 `positionsReadTimeoutMs` 时同样不下结论，并注明“两侧采样相隔过久”。
  - 契约：回复须为本配对子账户；数量符号与持仓方向一致、同一合约同一方向不重复、时间不超前本机时钟超过 `venueClockToleranceMs`、非零持仓最多 `MAX_POSITION_ROWS`（500）行、整个回复最多 `MAX_ANSWER_ROWS`（10000）行，否则整次读取记为失败；零持仓行不显示，也不校验其价格与时间。

## 人工处置（未结清划转记录损坏或结算持续出错）

配对说明出现“未结清划转记录损坏，需人工处置”或“未结清划转结算出错（连续 N 次：…）”、事件里有 `transfer-settle-failed` 时，执行器不会自行处置：该行一直未结清，所属配对与共用账户的配对一直不发送（账户也读不出时所有配对都不发送），其余配对照常。结算出错若只是暂时的（下一轮成功），说明会自动恢复，不需要处置。

1. 停止执行器进程（正常关闭会交还租约），确认没有其他实例在写这个数据目录。
2. 查看未结清的行与最近的失败事件：

   ```sql
   SELECT id, pair_id, state, created_at, json FROM transfers WHERE settled = 0;
   SELECT at, json FROM events WHERE type = 'transfer-settle-failed' ORDER BY seq DESC LIMIT 20;
   ```

3. 在交易所核对该配对两个子账户自 `created_at` 前 60 秒起的 USD1 划转流水与当前余额，自行判断这一笔是否到账。`state` 列为 `sending`、`unknown` 或 `acknowledged` 的行可能已经发出，执行器无法替你判断。
4. 等到该行 `created_at` 之后至少 10 分钟再处置：原请求最晚在发送后 155 秒（调用超时 35 秒 + 请求有效期 120 秒）之内被接受，之后的划转只看自己发送前 60 秒以内的流水，10 分钟后这一笔的流水不会再被别的划转当作候选，余额也应已反映它。
5. 把该行记为已结清（`json` 列保持原样留作审计）；记录只是个别字段有误且能确定正确值时，也可以改正 `json` 后让执行器自己结算：

   ```sql
   UPDATE transfers SET state = 'expired-unverified', settled = 1, version = version + 1 WHERE id = '<划转编号>' AND settled = 0;
   ```

6. 启动执行器。配对解除阻塞后按重新读到的余额规划，用新的请求编号；该行无法解析时不出现在最近划转列表里，超过保留期后删除。

风险：这样结清跳过了自动结算，没有标签、没有登记已用流水、没有结算冷却，也没有“余额须晚于结算时刻”的约束。第 4 步等待不足时，这一笔的流水可能被之后同额同向、结果未知的划转误认为自己的；这一笔实际到账而余额尚未反映时，下一次规划会按旧余额多划一次（资金仍只在该配对自有的两个子账户之间）。等够时间并在第 3 步核对过余额，可以避免这两种情况。

人工结清只改了 `state` 与 `settled` 两列，该行的 `json` 未变，所以“最近划转”里它仍显示处置前的状态，直到保留期清理时删除。接管或重启后，配对说明以“接管后有未结清的划转”开头，其后同样带出结算出错的原因。

配对记录损坏（`transfers.corruptPairs` 非空）：重新登记会以 `pair_corrupt` 被拒；同样先停机，改正 `transfer_pairs` 中该行的 `json`；没有任何划转记录引用它时也可以删除该行后重新登记。损坏期间它名下未结清的划转无法结算，会按上面的方式出现在失败事件里。

## 回滚（存储迁移 3）

迁移 3 只新增 `transfer_pairs`、`transfers` 两张表与 `transfers_unsettled`、`transfers_pair` 两个索引，不改动原有表。旧版本代码打开已升级的库会以 `newer_schema` 拒绝启动，不会误写。回滚到迁移 2 的代码有两种做法：

- 保留数据：停止执行器进程后对 `executor.sqlite` 依次执行下列语句，再启动旧代码。划转配对、划转记录与启停命令随之删除，两腿任务数据不受影响（`test/transfer.test.ts` 的升级测试执行同一组语句并核对结构回到迁移 2）。

DROP INDEX IF EXISTS transfers_unsettled;
DROP INDEX IF EXISTS transfers_pair;

DROP TABLE IF EXISTS transfer_pairs;

DELETE FROM schema_migrations WHERE version = 3;

回滚前须确认没有未结清的划转（`SELECT COUNT(*) FROM transfers WHERE settled = 0` 为 0）；否则结果未知的划转失去记录，无法再按流水结算。

## 已知限制

- 工作台金丝雀按钮（3.0d）只由替身与离线测试覆盖，未连过真实账户。它不经共享写者登记，旧系统（含自动规则）若同时对这两个账户的该合约下单，执行器会把对方委托当外部委托，金丝雀的自记持仓也不含它们：页面只要求操作者勾选承诺，系统不核实。系统也不检查是否开着旧系统的原油自动规则或共享写者是否持有这两个账户。金丝雀库位于工作台数据目录下，随工作台备份与恢复：从旧备份恢复会让自记持仓与累计上限回到备份时刻，恢复后须先做启动检查与核对。只读预览与真实运行之间行情可能变化，真实运行按新预览确认。

- 划转与 ADL 只按发送互斥：划转按发送前重读的余额规划，同配对的减仓单若在重读之后、划转落盘之前成交，所用余额不含这笔成交的保证金释放、手续费与已实现盈亏。模拟连接器的余额与持仓互不影响，测不出这一点；接真实账户前评估是否要求余额快照晚于同配对最近一笔减仓成交。
- 本机测量（Windows，非目标服务器）中，单次写事务持锁最大值与事件循环阻塞 p99 未达建议预算，原因是主线程同步提交在 `synchronous=FULL` 下等待 fsync；写入线程或批量提交留到阶段 2 选型。数值见盘点文档第 8 节。2.4b 在 Linux 开发服务器上的测量（第 8.1 节）中，回填线程持续写入约 136 秒的运行 WAL 峰值 116–403 MiB（两次运行），超过 64 MiB 建议值，一并留给 2.5 存储选型。目标服务器测量（2.4c，第 8.2 节，实测 2 核、3.57 GiB）中持锁最大 15–38 ms 达标，事件循环阻塞 p99 26–51 ms 处在 50 ms 建议值附近，WAL 只在慢 ASTER 长跑时超标（92.8 MiB）。阶段 2.5 决定保持主线程同步提交，不引入写入线程或批量提交；WAL 超标的原因推断为读取方连续占用快照，已加入 WAL 维护（见“关键语义”）：开发机默认 2 个读线程没有复现超标，8 个读线程复现后（213–353 MiB）修正为 19.8–20 MiB（第 8.3 节）；目标服务器尚未复测，那里的原因与修正效果都未验证。
- WAL 维护在主线程同步执行：一次截断在开发机上约 56–73 ms，读取方不让出时每次尝试实测约 0.37–0.39 秒，期间执行器不处理其他事情。它只约束本进程自己的检查，不能阻止其他进程长时间读这个库；备份（`VACUUM INTO`）期间同样无法截断。
- 追价 ACK 核对与认领按交易所的策略创建时间判断，时钟偏差容限只有 `adoptSkewMs`（5 秒）；交易所与本机时钟偏差超过它时，正常的追价 ACK 也会按创建结果未知转人工，认领同样被拒，接真实账户前须按交易所服务器时间校准或重新定容限。
- 追价子单是否结清依赖连接器回报的 `childrenSettled`；确认未创建依赖连接器 `listStrategies` 返回完整列表（分页读完，读不全须报读取失败），Bybit 真实连接器（3.0b）已实现但只经替身测试；创建结果未知的追价策略只能人工处理，没有自动判定未创建；新增字段只存于操作 JSON，未做存储迁移。
- 追价强制释放（`POST /api/jobs/:id/release-strategy`，`acknowledgeRisk: true`）是认领与确认未创建都走不通时的兜底：不做观察窗、列表或持仓核对，委托本地状态保持 `unknown` 并记下释放时刻，共享登记的建单按已确认（可能已执行）结清，之后可确认人工处理并释放合约。被释放的策略可能已在交易所创建并成交、甚至仍在运行，执行器不再认领、核对、停止或重发它，敞口与策略须由人工在交易所处理；该委托永不结清，所属任务的历史不进入保留期删除。
- ACK 后查询查无即按创建结果未知处理，不等待交易所可见性延迟；真实连接器若存在创建后短暂查不到的情况，会多出需人工处理的任务。
- 共享写者登记的协议缺口：账户一经认领永久归属该模块，没有交接或解除隔离接口（账户被隔离后登记操作也无法结清，只能人工恢复）；`executor.sqlite` 不在工作台恢复清单内。接真实账户（阶段 4）前须有对应协议能力。见盘点文档第 9 节。
- 登记结清只遍历当前绑定的账户：换绑后旧账户上的未决登记不会由本模块结清；登记库有未决操作时，结清会认领所有已绑定账户。
- 名义金额上限（3.0a）的口径与接真实账户前提：
  - 估算只在预览与确认时按当时盘口计；首腿市价或可立即成交的限价单在发送时由两腿守卫夹在保护界限内，但卖出首腿成交后的买入对冲腿按市价补发，行情上涨时实际金额可能超出上限。
  - 累计按数据目录计，不分环境与账户（任务表无环境列）：真实账户须使用独立、不重置的数据目录；同一目录先跑过的模拟任务会多占额度（安全方向）。缺价格保护界限的阶段 1 旧行按卖一价计，最多少算一个滑点带，只存在于模拟数据。
  - “委托全部未发送不计”依赖连接器分类：真实连接器在字节可能已经发出后绝不能报 `not-sent`，也不能在中止监听里同步报 `not-sent`（否则可能抢在调用超时的 `uncertain` 之前被采纳）。
  - 平仓不加仓依赖连接器：Binance 双向持仓模式不接受 reduceOnly，须靠 `positionSide` 保证只减不增。
  - 每次读取 `/api/state` 都从库内全部开仓任务重算累计，任务从不清理；金丝雀规模下可忽略。
- 真实连接器（3.0b）接真实账户（3.0c）前须核实或补齐：
  - 两个连接器都没在真实账户上跑过；Binance 统一账户（`portfolio-margin`）的 `papi` 端点照搬生产客户端，未经本模块验证。
  - 密钥权限、账户可交易状态与账户身份只在启动时检查一次（3.0c），运行中不复查；运行中有人改了密钥权限或账户状态，要到下次启动才发现。IP 白名单只核对“已绑定”，不核对绑定的是不是本机出口 IP。名义金额上限没有代码内硬顶（只受 `NOTIONAL_LIMIT_CEILING`），数值以配置为准、启动时打印。
  - Bybit 仍未核实（盘点第 47 项）：`/v5/strategy/order-list` 外层是否带 `nextCursor`（缺它时满页报读取失败，短页视为读完）；双向持仓账户上的策略与子单形状；部分成交后停止时子单的状态与数量；策略结束后其挂单是否短暂留在 `/v5/order/realtime`（会使下一批的发单前检查报外部委托）；多页时的分页；不带时间参数的运行中策略列表是否有时间限制。
  - Bybit 追价创建回执之后、策略记录可见之前若有延迟，执行器 ACK 后的首次查询会查无并按创建结果未知处理（见上文 ACK 后查询一条）。
  - Bybit 下单后的首个状态来自紧接着的一次查询，查不到时报为未成交的新委托，之后靠按客户订单号查询收敛；IOC 单在这段时间里实际已结束。
  - 端到端用例（`test/live-wiring.test.ts`）的替身交易所让每笔委托立即全部成交、追价由测试一次性结束，测不到部分成交、追价中途停止与对冲腿失败在真实账户上的形状。
  - 单次写入的最坏耗时可超过执行器 `callTimeoutMs`（35 秒）：Binance 读持仓模式与下单各可能含一次时间戳重发，每次请求上限 10 秒；Bybit 创建后还有跟进读取。超出时执行器按结果未知核对，方向安全但会多出待核对的委托；3.0c 接线没有收紧（没有真实耗时数据），金丝雀运行后按实测决定。
  - 时间戳重发时测得的交易所时钟偏移只用于签名，没有交给执行器；`adoptSkewMs` 仍用本机时钟比较交易所的策略创建时间（见上文追价 ACK 一条）。
  - Bybit `/v5/order/history` 不带时间参数只覆盖最近一段时间，很旧的委托会查无（同生产客户端），由执行器的持仓无痕迹核对兜底。
- 登录令牌不是一次性的，进程运行期间可重复使用；Windows 上文件权限 0600/0700 不生效，已存在的数据目录不改权限。
- 停止请求在首腿成交后也会阻止首笔对冲，任务转人工（保留敞口由人处理）；对冲腿不设价格上限（用户决定），极端行情下市价对冲可能远离预览价成交。
- ASTER 划转的未验证假设与限制（接真实账户前须逐项核实）：
  - 请求有效期：文档 nonce 窗口 60 秒加 60 秒时钟偏差，按 120 秒取值，未在线上验证；模拟连接器的 `requestValidityMs` 即此值。
  - 两侧流水的交易编号是否相同未验证；若不同，结果未知的划转永远无法确认，只会记为归属歧义并走长冷却。
  - 流水只能按侧、金额、时间归属：发送后出现的同额外部划转会被误认为本次已执行（`late_receipt_confirmed`），或使本次归属歧义；发送前基线读不到时保护更弱。到期后才出现的流水会使已到账的划转被记为未执行。回执不带交易编号的划转不登记已用流水，之后同额同向、结果未知的划转在没有发送前基线、且与前一笔的发送间隔小于约 2 秒（1 秒整秒截断加 `futureToleranceMs`；只有 `cooldownMs` 配到 2 秒以下才会出现）或交易所时钟超前时，可能被前一笔的流水误确认。`futureToleranceMs` 设为 0 会同时取消这里的时钟余量；`transferClockToleranceMs` 配到约 2 秒以下时流水读取窗口比该下界更紧，下界不起作用。标签只用于审计与选择冷却，之后的规划总是重读余额，最坏结果是资金在配对自有的两个子账户之间多移动或少移动一次（设计论证，不是交易所保证）。
  - 标签读取最多推迟 300 秒的上界、基线回看 60 秒、历史跨度 180 秒均沿用旧系统取值，未按真实接口重新论证。
  - 流水读取的完整性（分页读完、满页即不完整）只在模拟连接器实现；真实连接器须保证不完整时回报 `complete: false` 或读取失败。
  - 划转已接入共享写者登记（2.6c），但登记的协议缺口仍在：账户永久钉选给首个认领的模块，主账户也会被认领；登记的过期规则依据 ASTER v3 文档的 nonce 窗口（前后 60 秒）加 60 秒时钟容差，未经实盘验证。
  - 余额快照的时效按本机收到时刻（`receivedAt`）判断，不是交易所的数据时刻；真实连接器的 `receivedAt` 必须是本机收到应答的时刻，不得取自交易所时间，也不得超前（超前超过 1 秒的快照会被拒绝）；真实连接器须保证收到的余额反映此前已结算的划转，入账延迟上界未验证。配对停用、换账户不取消已发送的划转。
  - 已回执后余额在 300 秒内一直读不到时按回执结清，记录上没有划转后的余额；已结清的划转记录超过保留期后删除，审计须在保留期内导出。
  - 接真实账户前的前置项（真实 ASTER 划转契约测试、余额时序校验在真实连接器上的验证；共享写者登记已在 2.6c 接入）见盘点文档第 9 节第 39 项。
- ASTER ADL 应急处理的限制（接真实账户前须逐项处理）：
  - 证据冲突（同一交易编号前后不一致）只受阻并显示原因，没有页面处置入口，须人工处理数据。
  - 没有飞书告警；停止、受阻只在页面与事件里可见。
  - 减仓单与撤单已接入共享写者登记（2.6c）。本模块结果未知的划转在登记里最多挡住同组子账户 120 秒，期间减仓等待；但发送中被接管（崩溃或租约丢失）的划转登记停在发送中，不适用 120 秒过期，要等本地这笔划转结清（默认最长约 `readyAt` 加 300 秒的标签延后，约 7 分钟）才由结清步骤放行，其间减仓一直等待（不计入连续未发送）。登记临时拒绝期间每 `adlRetryMs` 落一行未发送批次，受事件 1800 秒运行时限约束。未知的减仓单在批次核对有结果（最长到观察窗结束）之前挡住该子账户的划转与其他写入。登记库的 120 秒过期同样会让新划转越过本模块已过期的未知减仓单：真实 ADL 连接器接入时须确认其签名有效期不超过 120 秒（目前只对划转连接器做启动校验）。
  - 成交历史窗口在相邻毫秒内仍是整页时无法再二分，该窗口一直保留待查（其后的时间照常扫描），其中超出一页的行只能靠推送发现；扫描窗口没有最大跨度限制，真实接口若限制查询跨度须拆分；内存推送队列上限 1000 条，溢出的只能靠历史扫描补回。
  - L054 的放宽判定（见“关键语义”）依赖交易所在成交时更新持仓时间；首次看到 ADL 成交就是撤单回报、且持仓在订单创建后因其他原因更新过时，过 120 秒后可能把尚未反映的成交当作已反映。
  - 减仓批次的“成交更少”时刻取规划时的持仓更新时间：结果未知的原单在之后的批次成交后才迟到成交时，放宽判定实际只剩 120 秒等待；这一分支（第一份回报即带成交且晚于持仓更新）模拟器不能直接构造，没有专门用例。
  - 预算沿用旧系统常量（`modules/aster/trading/adl.py`、`adl_recovery.py`），`adlWatchMs`、`adlNotSentLimit` 为新增，均未按真实接口重新论证。
- ASTER 持仓只读展示的限制：
  - 只有模拟连接器；真实接口的字段（如 `positionRisk` 的数量、开仓均价、未实现盈亏、更新时间）与请求权重未核对，杠杆、强平价、保证金模式未展示。
  - 结果只在内存，重启后首轮读取前显示“尚未读取”；没有历史与告警，两侧不一致只在页面可见。
  - 两侧采样各自计时：账户数超过并发上限时，同一轮内两侧可能相隔排队与读取时间；判断一致性不要求两侧采样同时，页面分别显示两侧采样时刻。
  - 45 秒有效期大于间隔与时限之和的前提是一轮读取不超过刷新间隔；账户多到一轮超过间隔（默认约 8 个以上不同子账户且多个读到超时）时，一次失败就可能让上次结果先过期而不再显示（只会少显示，不会显示过期数据）。
  - 关闭时不中止在途读取，入口最多等一次读取时限（8 秒）后退出。
